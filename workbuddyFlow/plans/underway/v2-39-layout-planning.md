> 关联前置：v2-36（分层布局，已归档）、v2-38（ELK 竖排为默认引擎，已交付）

## 1. 要解决的问题

用户口径（2026-09-18 原话）：**"这个排版就是对要生成的图形进行规划，遇到复杂的图形的时候应该分析包含什么模块，模块中包含什么，模块之间是怎么联系的。"**

### 1.1 现状：生成链路里没有"结构规划"这一步

```
LLM → SceneBinder(吸附) → SceneDeduper(去重) → LayoutEngine(纯几何) → GraphValidator → 下发
```

LLM 一次吐出一份**扁平**的元素列表（N 个图形 + M 条边，无层级、无分组），布局引擎只能"每层居中叠罗汉"。结果在复杂图上必然翻车：

- **跨层长边的标签压中间层节点**：标签渲染位置 = 箭头几何中点（Excalidraw 现算，后端改不了），"每层居中"的排布让中点必然砸在中间层节点上；
- **竖排把图收成一根窄条**：680x4820（20 图形），模块结构在视觉上完全消失。

### 1.2 为什么调间距治不了（已实测，勿重复试）

| 操作 | 标签压节点 | 结论 |
|---|---|---|
| 垂直层间距 ×16（340→5440px） | **2 → 2** | 无效，画布高 4820→76220px |
| 同层水平间距 ×3.75（80→300px） | **2 → 2** | 无效 |
| **层间横向错位 ×2** | **2 → 0** | **有效** |

几何不变量：垂直方向等比拉伸是**仿射变换，中点仍是中点** —— 跨 2 层的边，其中点永远落在中间那一层的高度上，与层间距无关（基准图 19 条带标签边里 4 条跨偶数层、15 条跨奇数层）。

**所以有效手段是"分区 + 层间错位"，而这正是排版步骤的产物 —— 不是调参数能拿到的。** 完整实验数据见 `state/activeLog/2026-09-18.md`。

## 2. 目标

给生成链路补上**排版步骤**：复杂需求先做**结构规划**（模块 → 成员 → 模块间关系），再按结构落几何，使复杂图的标签压叠归零、模块结构在画布上可见。

一句话验收：**同一句"画一个电商微服务架构图"，排版后标签压节点 = 0 且能一眼看出模块分区。**

## 3. 边界

- **允许新增**：`graph/ScenePlanner.java`（排版/分区，纯函数式、异常原样返回）；基准 fixture（带模块的复杂图）；契约/分区/布局的测试。
- **允许修改**：`schemas/scene.schema.json`（**加一个可选分组字段**）；`service/PromptService.java`（复杂图的分组要求）；`graph/ElkLayoutEngine.java`（两级布局路径 + **frame 几何重算**）；必要时 `graph/LayoutSpec.java`。
- **禁止改动**：
  - ❌ **不碰 `frame` 的 `children` 取舍** —— 2026-09-17 用户拍板的"方案 a"（契约不含 children，差异在前端适配层收口）保持不变。**注意：不碰 `children` ≠ 不碰 `frame` 的 `x/y/width/height`** —— 后者是几何、归布局管，本计划要改（见 5.4）；
  - ❌ **不碰绑定箭头策略** —— "线怎么画"属 v2-40（走线），本计划只管"节点怎么摆"；
  - ❌ **不碰编辑模式的坐标冻结语义** —— 既有图形坐标一个不许动，否则与 v2-37 `SceneDrift` 当场打架。

## 4. 分层边界

改动落在 `graph/`（新增排版层，位于 Deduper 与 LayoutEngine 之间）与 `service/`（提示词、链路编排），**不触碰** `client/`（LLM 供应商）、`session/`（会话存储）、`controller/`。

切法理由：排版是**纯几何/拓扑决策**，输入输出都是场景 JSON，与"谁提供 LLM""存在哪里"无关 —— 放在 `graph/` 才能让两个 `LayoutEngine` 实现共享它，也能被基准工具单独调用。

## 5. 方案（三件事，按序）

### 5.1 结构表达：给图形加一个可选分组字段

契约现状：所有元素 `additionalProperties: false`，`shape` **没有**分组字段；`frame` 有 `name` 但无 `children`。

**方案：`shape` 上新增可选 `group: string`（模块名，自由文本）。**

- 语义层分组，**不是渲染层容器** —— 与"frame 不含 children"的决定不冲突；
- `frame` 的角色降为**可选的可视化边界**（`name` = 模块名），有没有都不影响分区；
- 兼容性：可选字段，旧场景 / 不分组时完全不受影响。

### 5.2 模块从哪来：LLM 为主 + 后端兜底（降级设计）

| 优先级 | 来源 | 说明 |
|---|---|---|
| ① | **LLM 标注** | 图形数超阈值时，提示词要求把节点归入 2~5 个模块并写 `group` |
| ② | **后端聚类兜底** | LLM 未给 / 给得不成形 → 按拓扑连通性 + 标签前缀聚类 |
| ③ | **不分组** | 兜底也拿不到合理分区 → 走今天的单层布局（行为与现状一致） |

**触发阈值**：图形数 ≤ 12 时**不做分组** —— 简单图不该为不存在的复杂度买单，也避免把"加审批节点"这类小图排变样。

### 5.3 按结构落几何：两级布局（不引 ELK 的 compound graph）

1. **组内**：对每个模块单独跑一次现有 ELK 竖排 → 得到模块的局部坐标与包围盒；
2. **组间**：把每个模块的包围盒当作**一个大节点**，再跑一次 ELK → 决定模块之间的相对位置与间距；
3. **合并**：组局部坐标平移到组间位置；组间留出**比层间距更宽的通道**（跨组边的标签落点就吃这条通道）。

为什么不直接用 ELK 的 `hierarchyHandling: INCLUDE_CHILDREN`：compound graph 要处理父子坐标系换算与跨层边路由，踩坑面大；两级布局把同样的事拆成两次**已验证可用**的单层调用，实现与测试都简单得多。

### 5.4 frame 几何必须随节点一起重算（**本计划新增，实测缺口**）

> 来源：2026-09-18 复杂提示词电池实测（`tools/e2e/e2e_prompt_battery.py`，题源 `docs/复杂提示词测试集.md`）。
> **修正本节原方案里"`frame` 有没有都不影响分区"这句错误假设。**

**实测事实**：`ElkLayoutEngine.SHAPE_TYPES` 只有 `rectangle / ellipse / diamond`（`ElkLayoutEngine.java:63`），**`frame` 不在布局节点集合里**。于是同一个场景里出现两套互不相干的坐标系：

- **节点** = ELK 重排后的坐标，**42/42 全落在 20px 吸附网格上**；
- **frame** = LLM 给的种子值，原封不动，**4 个里只有 1 个恰好落在网格上**。

后果（题 2「电商订单处理全流程」143 元素实测）：

| 指标 | 实测值 |
|---|---|
| frame 两两重叠 | **5 对**（4 个 frame 里 6 对组合，5 对相叠；子流程框互相压 40% / 30%） |
| 图形跑出所有 frame | **24 / 42** |
| 图形同时落在 ≥2 个 frame 内 | **6 个** |
| 主流程框 | x 50~1550 / y 30~930，而节点包围盒 x 0~2160 / y 0~1740 |

**所以 frame 不是"有没有都行"的可选装饰，而是会主动把画面搞乱**：框和内容对不上、框与框互相压。LLM 只要按"用不同背景色区分模块 / 用虚线框包围子流程"这类要求输出了 frame，这个错位就是必然的。

**修法（两条，选一，需拍板）**：

- **A. frame 当容器参与布局**：把每个 frame 视为一个模块容器，节点按 `frameId`/几何归属进容器，容器随内容一起摆 —— 本质上就是 5.3 的"两级布局"，frame 的包围盒正好等于组的包围盒 + 内边距；
- **B. 布局后重算 frame 几何**：布局不动 frame，但在写回坐标之前，按"几何上落在框内 / 已在框内的节点"重算每个 frame 的包围盒 —— 改动小，但分组依据仍是"LLM 种子坐标的巧合"，不可靠。

**建议 A**（B 依赖 LLM 种子坐标恰好分组正确，正是本次实测证明不可靠的东西）。A 与 5.3 天然合流：**模块的包围盒 = 它的 frame 几何**，一份计算两处用，不需要额外的"分组 → 画框"逻辑。

## 7. 步骤

2. **提示词加要求**：`PromptService` 在图形数超阈值时要求分组（含"模块名用业务词、2~5 个、每个模块至少 2 个图形"这类约束）；补 prompt 断言测试；

## 8. 验收口径

缺一条不算完成：

1. **标签压叠归零**：带模块 fixture 上，标签压节点 = 0 且标签互叠 = 0（现状 2 / 2）；
2. **分区可见**：每个模块的成员在几何上聚成一块 —— 模块内相邻图形间距 < 模块间最小间距；
3. **跨组标签落通道**：跨模块边的标签不落在任何模块的图形上；
4. **长宽比合理**：整图包围盒长宽比落在 [0.5, 2]（现状竖排 7.09）；
5. **简单图零回归**：图形数 ≤ 12 的图，坐标与今天完全一致（不分组路径未被触动）；
6. **编辑模式零回归**：既有图形坐标一个不动（v2-37 `SceneDrift` 不报 issue）；
7. **真实 LLM 端到端**：round1 同 prompt 复跑，肉眼 + 指标双确认改善；
8. **门禁全绿**：后端测试 + checkstyle 0 违规 + 前端三绿 + 冒烟 + E2E；
9. **frame 与内容对齐**（5.4 的验收，复杂提示词电池同时是回归工具）：**frame 两两重叠 = 0**、**跑出所属模块 frame 的图形 = 0**、**落在 ≥2 个 frame 内的图形 = 0**。现状 5 对 / 24 个 / 6 个。
