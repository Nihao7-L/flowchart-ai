# roadmap.md — 执行顺序（S0~S6）

> 只回答一个问题：**这些模块按什么顺序做、做到哪一步算"我能亲眼看见"。**
> 编号规则见第四节：**M / v2-N 是身份，S 是时间**，两套编号并存、互不替代。

## 一、为什么要有这份文件

`plans/masterPlan/` 下的 `mN-` 是**按代码维度（改哪些包）**切的模块，不是执行顺序。历史排法（M0→M1→…→M7）等于"按技术层切"：六个待做模块里五个是纯后端，前端被压到倒数第二 —— 结果是做完 M1 之后要连续跨 M2 / M3 / M4 / M5 盲写后端，手上只有 JSON 和测试数字，看不见一张图。

本文件改用**按可验证的能力切**（垂直切片 vertical slice：一次交付一条从头到尾能跑通的最小能力，而不是交付一层代码）。每一阶段都必须有一个人能亲手点出来的验收动作，否则这个阶段就是没交付。

模块编号与 v2-N 编号**一个都不动**。

## 二、阶段 × 模块映射

| 阶段 | 一句话 | 模块 | 交付的能力 | 你怎么亲自验 |
|---|---|---|---|---|
| **S0** 底座 | 改动自动被验 | M0 | 门禁 + CI + 文档体系 | 已闭合 ✅ |
| **S1** 看得见 | 说一句话，图上屏 | M1 + M6a | NL → IR → 画布 | 起前后端 → 输入"画一个登录流程图"→ 画布出现正确的图；再说"再加一个审批节点"→ 图上多一个 |
| **S2** 更准 | 出图能引用你的文档 | M2 | RAG 知识注入 | 丢一份文档进去、提相关问题 → 图里体现文档内容，且能指出来源 |
| **S3** 能改 | 人和 AI 都能改这张图 | M3 + M6b① | 双通道 + Diagram Tools | 手动拖个节点 → 后端坐标已更新；对话说"把 A 改成 B"→ 图跟着变；**两条路不互相覆盖** |
| **S4** 会规划 | 复杂需求自动多步完成，过程可见 | M4 + M6b② | 真 ReAct + 过程可视化 | 输入"画一个电商系统架构"→ 界面上看到思考 / 工具 / 校验事件逐步推进 |
| **S5** 不丢 | 刷新、重启图还在 | M5 | Redis 持久化 + 降级 | 重启后端，图完整恢复 |
| **S6** 可追踪 | 线上问题查得到 | M7 | Trace / 指标 / 审计 / 探针 | 一次请求的日志能用 traceId 串起来 |

## 三、两条关键决策（对应模块范围的调整）

**决策 1：M6 拆两个文件、内容分三段随阶段交付。**

| 拆出的块 | 内容 | 归到 | 文件 |
|---|---|---|---|
| **M6a** 渲染镜像层 | v2-23 设计稿 + v2-24 的只读渲染（IR → 画布） | S1 | `m6a-render.md` |
| **M6b①** 双通道交互 | v2-24 的 `onChange` 坐标回写 + v2-25 AI 改图 | S3 | `m6b-interaction.md` |
| **M6b②** 过程可视化 | v2-26 SSE 事件驱动界面 | S4 | `m6b-interaction.md` |

原 `m6-frontend.md` 已拆分为上述两份并删除。这样 M6a 在 S1 完成时即可归档，不必等 M6b 拖到 S4 —— 保住"模块整体完成才归档"的约定。

**决策 2：M5 的"内存版存储"下沉到 M1。**

- M1 的 v2-11 在交付 `/api/chat`(SSE) 时**一并给出最小会话上下文**（`SessionStore` 接口 + 内存实现 + `PATCH /api/model/positions`），符合 ADR-2（真相源在后端）。理由：`chat` 天生是多轮的，"再加一个节点"必须让后端记得当前这张图长什么样。
- M5 的 v2-21 因此收窄为"**Redis 实现 + 自动降级切换**"，不再是"从零做存储"。
- **连带结论**：S3 的"人拖拽 → 坐标回写"必须随 M6b① 一起做，**不能等 M5** —— 因为 S3 要验证的正是"人拖的那条路和 AI 改的那条路写同一份数据"这个最核心的架构假设。内存态即可（重启会丢，S5 补持久化），但验证不能等。

## 四、编号规则（重要，不要混）

- **`M0~M7`（含拆分出的 `M6a` / `M6b`）= 模块身份**：对应"改哪些代码包"，与 `plans/masterPlan/` 文件一一对应。模块**整体完成**才归档。
- **`v2-1 ~ v2-30` = 任务身份**：已完成的那批（v2-3 门禁 / v2-5 CI / v2-7 checkstyle）已与归档件绑死，**永不重编号**（归档件不可回改，见 `state/completed/README.md`）。
- **`S0~S6` = 执行顺序**：本文件定义的"时间轴"。**一个模块可跨多个阶段**（M6 跨 S1 / S3 / S4），**一个阶段可由多个模块组成**（S1 = M1 + M6a）。

要调整先后，**只改 S 的顺序，不动 M 与 v2-N**。

## 五、代价与风险（不粉饰）

1. **S1 变重了**：M1 + M6a 一起交付，第一个可见产品的周期比原计划长。这是"尽早看见"的必要投入。
2. **M1 的范围膨胀**：多了内存会话上下文这一块。必须写死在 M1 边界里，否则会往"顺手把 M5 做了"的方向滑。
3. **一个新常态**：一个模块可跨多个阶段（M6）。现有约定是"模块整体完成才归档"，所以 M6 必须拆文件，否则永远归不了档。
4. **文档一致性成本**：阶段标注要在模块计划、`coreFun.md`、`architecture.md` 三处同步；改一处忘一处就会出现"文档自相矛盾"。
