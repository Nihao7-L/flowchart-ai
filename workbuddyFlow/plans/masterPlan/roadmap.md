# roadmap.md — 执行顺序（S0~S6）

> 只回答一个问题：**这些模块按什么顺序做、做到哪一步算"我能亲眼看见"。**
> 编号规则见第四节：**M / v2-N 是身份，S 是时间**，两套编号并存、互不替代。

## 一、为什么要有这份文件

`plans/masterPlan/` 下的 `mN-` 是**按代码维度（改哪些包）**切的模块，不是执行顺序。历史排法（M0→M1→…→M7）等于"按技术层切"：六个待做模块里五个是纯后端，前端被压到倒数第二 —— 结果是做完 M1 之后要连续跨 M2 / M3 / M4 / M5 盲写后端，手上只有 JSON 和测试数字，看不见一张图。

本文件改用**按可验证的能力切**（垂直切片 vertical slice：一次交付一条从头到尾能跑通的最小能力，而不是交付一层代码）。每一阶段都必须有一个人能亲手点出来的验收动作，否则这个阶段就是没交付。

模块编号与 v2-N 编号**一个都不动**。

## 三、两条关键决策（对应模块范围的调整）

**决策 1：M6 拆两个文件、内容分三段随阶段交付。**

**决策 2：M5 的"内存版存储"下沉到 M1。**

- M1 的 v2-11 在交付 `/api/chat`(SSE) 时**一并给出最小会话上下文**（`SessionStore` 接口 + 内存实现 + 画布现状同步入口，2026-09-16 起为 `PUT /api/model/canvas`），符合 ADR-2（真相源在后端）。理由：`chat` 天生是多轮的，"再加一个节点"必须让后端记得当前这张图长什么样。
- M5 的 v2-21 因此收窄为"**Redis 实现 + 自动降级切换**"，不再是"从零做存储"。
- **连带结论**：S3 的"人拖拽 → 坐标回写"必须随 M6b① 一起做（实际已随 v2-24a / v2-34 在 S1 交付），**不能等 M5** —— 因为 S3 要验证的正是"人拖的那条路和 AI 改的那条路写同一份数据"这个最核心的架构假设。内存态即可（重启会丢，S5 补持久化），但验证不能等。

## 四、编号规则（重要，不要混）

- **`M0~M7`（含拆分出的 `M6a` / `M6b`）= 模块身份**：对应"改哪些代码包"，与 `plans/masterPlan/` 文件一一对应。模块**整体完成**才归档。
- **`v2-1 ~ v2-30` = 任务身份**：已完成的那批（v2-3 门禁 / v2-5 CI / v2-7 checkstyle）已与归档件绑死，**永不重编号**（归档件不可回改，见 `state/completed/README.md`）。
- **`S0~S6` = 执行顺序**：本文件定义的"时间轴"。**一个模块可跨多个阶段**（M6 跨 S1 / S3 / S4），**一个阶段可由多个模块组成**（S1 = M1 + M6a）。

要调整先后，**只改 S 的顺序，不动 M 与 v2-N**。

## 五、代价与风险（不粉饰）

1. **S1 变重了**：M1 + M6a 一起交付，第一个可见产品的周期比原计划长。这是"尽早看见"的必要投入。
2. **M1 的范围膨胀**：多了内存会话上下文这一块。必须写死在 M1 边界里，否则会往"顺手把 M5 做了"的方向滑。
3. **一个新常态**：一个模块可跨多个阶段（M6）。现有约定是"模块整体完成才归档"，所以 M6 必须拆文件，否则永远归不了档。
4. **文档一致性成本**：阶段标注要在模块计划、`coreFun.md`、`architecture.md` 三处同步；改一处忘一处就会出现"文档自相矛盾"。

### 布局引擎：自研 `graph/SceneLayout` → 可选升级 ELK（Java 版）

- **决策沿革**：2026-09-18 上午用户拍板"ELK 作备用、暂不引"；**同日下午用户看到 43 元素真实出图后改判** —— 图里菱形分支线交叉、红字标签成堆压在一起，观感不可接受。改判为**引入 ELK 并建量化基线对照**，用数据决定默认引擎。
- **落地形态**：`LayoutEngine` 接口 + 两个实现（`SceneLayout` 自研 / `ElkLayoutEngine`），由 `chartflow.layout.engine=elk|legacy` 切换；`GenerationService` 只依赖接口。
- **默认引擎的最终拍板（2026-09-18 用户）**：**默认 `elk`，取竖排（`WrappingStrategy.OFF`）**，自研降为 `legacy` 备用实现。理由是三方对照里竖排"一列直下、层间短连线、标签不打架"最好读；折行虽把画布压成 1860×1760，却让长边跨列横穿整图，观感更差。默认值写在**代码侧**（`@ConditionalOnProperty(matchIfMissing = true)`）而不是 `application.yml` —— 后者被 `.gitignore` 忽略，只写那里换台机器就失效。
- **量化基线**（2026-09-18 实测，同一张 20 图形 / 27 边 / 19 条带标签的登录流程图；工具 `workbuddyFlow/tools/layout-bench/`）：

| 指标 | 自研 | ELK 竖排 | ELK 折行 |
|---|---|---|---|
| 图形重叠 | 0 | 0 | 0 |
| 边交叉 | 0 | 5 | 6 |
| 长宽比（高/宽） | 0.65 | 6.00 | 0.89 |
| 标签压节点 | 8 | 2 | 2 |
| 标签互相叠 | 7 | 1 | 0 |
| 包围盒（px） | 3104x2020 | 680x4820 | 1860x1760 |

- **结论**：**标签落位与整体规整度 ELK 明显更好**（三方渲染对比见 `workbuddyFlow/tools/layout-bench/compare.html`：ELK 竖排一列直下、层间短连线；自研是"主干横排 + 分支竖堆 + 长斜线穿图"）。"边交叉"ELK 反而略差，根因是下面那条硬约束。
- **一条硬约束，决定了换引擎的天花板**：本项目箭头是 Excalidraw **绑定箭头**（只存 `{start:{id},end:{id}}`，由两端现算直线），所以 ELK 的**正交边路由与虚拟节点绕行拿不到** —— 除非放弃绑定改存折线点，而那会丢掉"拖节点时箭头自动跟随"。**换引擎的收益上限是"节点怎么摆"，不包括"线怎么画"。**
- **为什么不是 elkjs / dagre**：这两个是 JS 库（elkjs = ELK 内核用 GWT 转译出的 JS 版），只能在前端或 Node 侧算 —— 与"几何唯一真相源在后端"（ADR-2）冲突：前端算 = 多一个真相源（且 A2 已删前端布局兜底）；挂 Node 亦 = 多一个进程与部署单元。真要换，换 **Java 版 ELK**（`org.eclipse.elk`，EPL 许可），它能留在同一个 JVM 里。
- **自研当前的代价（如实记，不粉饰）**：不做多轮交叉最小化；**不做边路由** → 多条长边会共用同一列通道，密图里出现"线叠线"，边标签还可能落到节点标签上（2026-09-18 真实出图实测：共用通道 7 对、一处 `支付请求` 压 `订单服务` 20×25px；截图见 `state/activeLog/2026-09-18.md`）。
- **触发阈值（出现任一即开工，另开 v2-N 计划）**：
  1. 单张图元素数稳定超过 50；
  2. 需要嵌套子图（大框套小框，compound graph）；
  3. 需要连线绕开节点（正交路由）而不是斜穿；
  4. 图开始被当"依赖图 / 拓扑图"看，而不是"示意图"看。
- **换引擎的实际成本（2026-09-18 已付费，记账备查）**：ELK 拖进 EMF / Xtext 一串 jar；**它自己的 pom 漏声明 Xtext**，纯 Maven 项目必须手动补 `org.eclipse.xtext:org.eclipse.xtext.xbase.lib`，且版本要与 ELK 构建时一致（ELK 0.12.0 用 **2.36.0**；用 2.44.0 会因 class 文件版本过高在 Java 17 上 `UnsupportedClassVersion` 崩）；脱离 Eclipse 后算法元数据靠 jar 内 `META-INF/services` 的 SPI 自动注册，但**不能用 `ElkLayered` 直接 `doLayout`**（那要内部 LGraph），入口是 `RecursiveGraphLayoutEngine`；Excalidraw 契约与 20px 网格吸附仍要自己适配（`LayoutSpec`）。
- **铺路两件事的落地情况**：① `LayoutEngine` 接口**已抽**（`GenerationService` 只依赖接口）；② golden fixture 与指标基线**已建**（`workbuddyFlow/tools/layout-bench/`：fixture + `LayoutBench` 指标 + `render_compare.py` 三方渲染对比）。
- **仍未解决（新登记，触发即开工）**：跨层长边仍是直线斜穿 —— 回边（如"转到手机验证 → 验证手机号"）会横穿整幅图。可行方向：① 只对回边用显式折线沿图外侧绕行；② prompt 层面减少跨层回边；③ 折行布局已能改善画布比例，代价是跨列长线变多。
- **竖排落地后新测到的副作用（2026-09-18 实图，`tools/e2e/e2e_real_llm_layout.py`）**：微服务图（6 图形 / 9 长边）实测 **标签互相压叠 7 对**（基准图只有 2 对）。根因不是引擎：**跨 2 层以上的长边（"各服务 → 数据库"）其标签被 Excalidraw 钉在箭头几何中点**（AI 标签带 `containerId`，位置由容器现算、后端改不了），而竖排把整图收成一根窄列（458x840），中点必然落在中间层的节点上。**这是"竖排换来的整齐"与"长边标签"的直接冲突**，与绑定箭头那条硬约束同源。可行方向：① 长边标签改为**不绑定**（后端自己算落点、避让节点），代价是拖节点时标签不跟随；② 减少跨层长边（prompt 层面把"服务 → 数据库"改成逐层串联或共用一条干道）；③ 回到折行/更宽的主方向，用横向空隙容纳长边中点。

### 布局质量诊断：间距不是解药（2026-09-18 实测，**修正上条结论**）

> 触发：用户质问"real-llm-round1.png 拉开一些组件之间的距离不就能避免重叠吗，怎么还是这么多重叠"。此前只做过"三方对照（选引擎）"，**没做过同一引擎下改动间距的敏感性分析** —— 这次补上，结论与直觉相反。

以 ELK 竖排产物（20 图形 / 19 条带标签边）为底做纯几何扫描（标签位置 = 两端图形中心连线中点，宽 20px/汉字、高 25px）：

| 实验 | 操作 | 标签压节点 | 标签互叠 | 代价 |
|---|---|---|---|---|
| A | 只拉大**垂直层间距** 340→5440px（16 倍） | **2 → 2（不动）** | 1 → 1（不动） | 包围盒 4820→**76220px**（15.8 倍） |
| B | 只放大**同层水平间距** 80→300px（3.75 倍） | **2 → 2（不动）** | 2 → 1 | 画布宽 590→710 |
| C | 等比放大**整体水平坐标**（×2） | **2 → 0** | — | 画布宽 590→1200 |

**几何不变量（为什么 A 必然无效）**：绑定标签的渲染位置就是箭头几何中点（`sceneAdapter.ts:605-607` 的 09-17 像素级实测已证）。垂直方向等比拉伸是**仿射变换，中点仍是中点** —— 跨 2 层的边，其中点永远落在**中间那一层的高度**上，与层间距大小无关。基准图 19 条带标签边里 **4 条跨偶数层**（中点必然落在层高上）、15 条跨奇数层（中点在层间空隙，本来就不压）。**奇偶性由拓扑决定，调间距改不了。**

**B 为什么也无效**：被压的 2 条边都跨 2 层，而每层各自居中 → **层间没有错位**，挪开同层邻居不改变"中点 x 落在中间层那个节点的 x 范围内"。C 有效，是因为它同时放大了**层与层之间的水平错位**。

**逐条定位（现状）**：压叠 2 条 —— 「否」压「滑块验证」（边 `n-risk→n-need2fa`，跨 2 层）、「注册未完成」压「完成二次验证（和生物识别）」（边 `n-register→n-fail`，跨 2 层）；标签互叠 2 对。**两条压叠边都是业务上的"跳步边"（跳过 / 失败重试），不是人为错误。**

**结论修正**：上条把压叠归为"与绑定箭头硬约束同源（后端改不了）"——**过于悲观**。绑定箭头只限制"**线怎么画**"（直线），**不限制"节点怎么摆"**；压叠的真因是**排布方式**（每层居中叠罗汉、层间无错位），属于可改范畴。正确归因是：**缺一个"排版"步骤**（见下）。

**顺带确认一个真缺陷（未修，待拍板）**：`LayoutSpec.mainGapFor()` 会按**最长边标签宽度动态放大层间距**（100 → 340），而 **`SIBLING_GAP` 是写死的 80** —— 两者不对称。80px 只够 4 个汉字（4×20），而"支付请求路由"6 字 = 120px → 必然横跨到相邻节点上；这正是 round1 截图里「用户服务」与「支付请求路由」相叠的形态。修法：给 `SIBLING_GAP` 加一个与 `mainGapFor` 对称的动态放大。

### 复杂提示词电池首跑：五个新发现（2026-09-18 实测）

| frame 审计 | **4 个 frame，只有 1 个落在 20px 网格上；frame 两两重叠 5 对；24/42 图形跑出所有 frame；6 个图形落进 ≥2 个 frame** | 2 个 frame 全空 |

**发现 1（高，已确认缺陷）：`frame` 完全不经布局引擎 → 框与内容各用一套坐标系。**
`ElkLayoutEngine.SHAPE_TYPES` 只有 `rectangle / ellipse / diamond`（`ElkLayoutEngine.java:63`），frame 不在内。证据是网格：**节点 42/42 全落在 20px 吸附网格上**（布局产物），**frame 4 个里只有 1 个落网**（仍是 LLM 种子值 1500x900 / 420x360 …）。于是"主流程框"停在 x 50~1550 / y 30~930，而节点包围盒已经跑到 x 0~2160 / y 0~1740。**只要 LLM 按提示词输出了 frame（"用虚线框包围子流程"这类要求极易触发），错位就是必然。** → 已写进 `plans/underway/v2-39-layout-planning.md` 新增的 **5.4**（含两条修法，建议"frame 当模块容器参与两级布局"）与**验收第 9 条**。

**发现 2（高，已确认缺陷）：契约没有时序图原语 → 图形数 0 → 布局引擎整体跳过。**
题 4 的模型只用 `text + arrow + frame` 表达时序图（参与者、生命线、loop 框全靠文字与空框仿造）。`layout()` 第一句就是 `if (shapes.isEmpty()) return json;`（`ElkLayoutEngine.java:99-101`）—— **布局一步没跑，LLM 的种子坐标原样上屏**，26 个 text 互相压 72 对，两个 loop 框全空。即"布局"这条路对**任何不含图形的图**是零收益。根因是**契约只有 7 种元素、没有时序图/甘特图原语**（题 8 甘特图同理）。→ 登记为待决：是否在提示词层**拒绝**无法用契约表达图种（先说清"画不了"）而不是硬凑。

**发现 3（中，已确认缺陷）：多行提示词被输入框吃掉换行。**
聊天输入框是 `<input>`（单行，`ChatPanel.tsx:78`）→ 浏览器的 value 清洗会**剥掉所有 `\n`**。实测：1144 字 / 62 行 → 送达 1144 字 / **1 行**；1374 字 / 75 行 → **1 行**。而 `docs/复杂提示词测试集.md` 这类提示词的**结构信息全在缩进与换行里**（`├──` 树）。用户粘贴一段文档即静默降级为一行。→ 待决：输入框换 `textarea`，或发送前把换行折成 ` / ` 之类可读分隔符。

**发现 4（中，约束失效）：提示词里"元素总数 ≤40"没有被遵守，后端也没有任何兜底。**
题 2 实际产出 **143 个元素 / 42 个图形**（提示词上限 3.5 倍），且 `GraphValidator` **没有元素数校验**，`GenerationService` 也没有 —— 约束纯靠 LLM 自觉。它这次无视了，但仍然画出可读的图（说明上限该按**可读性**而非性能来定）。→ 与 v2-39 的"排版"同一族：**该做的是结构规划，不是设上限砍需求**。

**发现 5（观测缺口）：校验失败只报数量，不报内容。**
两条题都在第 1 轮校验失败（1 个 / 2 个问题）并因此多耗一整轮 LLM 调用（约 130 秒），但 SSE 只发"第 N 轮校验失败: K 个问题"，**issue 明细既不进前端也不进日志**（`GenerationService` 只 `LOG.warn` 数量）。复盘时只能靠猜。→ 待决：把 issue 明细并入 validation 事件或至少落日志。

**顺带**：两条题的硬断言（NaN / 图形重叠 / 空图）全过 —— 说明**执行链路是稳的，问题都在"图的语义与结构"层**，正是 S1b（排版）要处理的层。

## 七、两个缺失的步骤（2026-09-18 用户提出，**术语已纠正**）

> 用户原话：「这个可读性测试不应该这样叫，应该叫**排版**」「我们还缺少一个**排版**的步骤和**线条不只是直线**的两个步骤」。
> 此前的提法"可读性约束 / 主流程 ≤15~20 节点"**作废** —— 那是"设上限砍需求"，不是"结构化地排"。

**步骤一：排版（结构规划）**
- **定义**（用户口径）：对要生成的图形**先做规划** —— 复杂需求要先分析**包含哪些模块、模块中包含什么、模块之间怎么联系**，再落几何。
- **现状缺口**：生成链路是 `LLM → Binder → Deduper → 布局(纯几何) → 校验`，**没有任何结构规划环节**；LLM 一次吐出扁平的元素列表，布局只能"每层居中叠罗汉"。提示词里对图粒度**只有一条**"元素总数 ≤40"（交付/性能约束），**没有分模块的要求**。
- **为什么它能治压叠**：实验 C 证明有效手段是**层间错位 / 分区**。有了模块分区，跨层长边的中点就能落进**区间的空白通道**，而不是节点上；同时解决竖排过长（680×4820）—— 模块内竖排 + 模块间并列，长宽比自然合理。
- **技术上对应**：契约里已有 `frame` 类型（容器框）；ELK 原生支持 **compound graph**（`hierarchyHandling: INCLUDE_CHILDREN`）→ 模块内子布局 + 模块间外层布局。**这正是第六节登记的触发阈值 #2「需要嵌套子图」，已由本需求触发。**

**步骤二：走线（连线不只是直线）**
- **现状硬约束**：Excalidraw 0.18.1 里**绑定箭头 ⇔ 直线**（UI 无折线入口，latest 即 0.18.1，升级无解）。**2026-09-18 探针补充实测**：不绑定 + 多段 `points` 的折线**能正常渲染**（截图 `probe-contract-capacity.png` 里有 3 段折线）—— 缺的不是渲染能力，而是"后端算路径 + 拖动后重新路由"这套逻辑；另实测**端点形状（如数据库鸦脚）与绑定可以共存**，不必为拿到端点形状而放弃绑定。
- **要折线必须**：箭头**不绑定** + 后端算 `points` 走行点；代价是拖节点时箭头不跟随 → 需在 `PUT /api/model/canvas` 回写链路里做**重新路由**。
- **与步骤一互锁**：排版决定"哪里有空地"，走线决定"怎么走到那里"。

**优先级与模块归属**：两者都是生成期的结构与几何决策，与 v2-36 / v2-38（布局）同族。**2026-09-18 用户拍板：排版先行**（走线随后）。计划已落 `plans/underway/v2-39-layout-planning.md`（状态：**待审**，含 4 项动码前须确认的问题）；对应新阶段记为 **S1b**（见第二节表格）。模块归属建议新开 `m8-layout-planning.md` —— `m1-generation` 已归档，按"模块整体完成才归档"的约定不宜回改。


**底层缺口（不是步骤，是底座）：契约容量**
- **2026-09-18 用户判断**：「画不了复杂的图形……`scene.schema.json` 太过于局限、太过于死板，就算现在再怎么测试都没用」。**实测成立**：Excalidraw 0.18.1 支持 12 种箭头端点（含数据库鸦脚）、多层 `groupIds`、可嵌套 `frame`、`roundness`、图形虚线、`verticalAlign`、`link`、多段折线，**契约一项都没传过去**（契约只有 6 类可用元素、约 30 个字段）。
- **连锁后果**：测试集 9 条题里 **8 条要求「嵌套」**，而契约的嵌套表达能力≈0（`frame` 无归属、无 `groupIds`）→ 图只能画成扁平一堆框。
- **处置**：能力矩阵与图型语法落 `docs/diagram-grammar.md`；模块计划 **`plans/masterPlan/m9-contract-capacity.md`（2026-09-18 拍板新开）**；活跃项 `state/active/v2-40-contract-capacity.md`；对应新阶段 **S1a**（见第二节表格）。**S1a 先行于 S1b**（排版需要 `group` 语义作输入）。
- **同时修正一处**：`frame.children` 被适配层补空数组，导致框与内容**归属断裂**（实测成员 `frameId` 恒为 null）—— 详见 `docs/constraint.md` 技术约束与 `docs/diagram-grammar.md` 第 4.1 节。
- **2026-09-18 用户拍板（5 项）**：

  | # | 问题 | 决定 |
  |---|---|---|
  | 1 | 契约扩展原则 | **语义编译**（LLM 只说语义，后端编译成渲染字段） |
  | 2 | P0 是否立刻做 | **立刻做** → ✅ 已完成（125 测试 / 0 checkstyle 违规 / 前端三绿 / 冒烟 12/12） |
  | 3 | 图型优先级 | **先做部署图 / 决策树 / 甘特图**（见下） |
  | 4 | `group` 写法 | **自由文本**（`shape.group: "订单域"`） |
  | 5 | 模块归属 | **新开 m9**（M1 已归档，不回改） |

- **⚠️ 三类优先图型的缺口性质完全不同**（不要当成一件事做）：

  | 图型 | 缺什么 | 归哪个子计划 | 难度 |
  |---|---|---|---|
  | 部署图 | 嵌套集群：多层 `groupIds` + 容器虚线框 + 分区布局 | P1（层次）＋ v2-39 排版 | 中 |
  | 决策树 | 分支标签避让 + 子决策组嵌套 | **布局层**（`SIBLING_GAP` 写死 80 是直接原因）＋ 走线 | 中 |
  | 甘特图 | **时间轴 + 任务条** —— 契约里没有"条"这个原语 | **P3（图型语法）**，需新增语义原语 | **高** |

  甘特图不是"多一个字段"能解决的：Excalidraw 也没有甘特原语，只能用圆角矩形近似 +
  时间轴刻度。要先把"甘特图在我们的系统里长什么样"定下来（语义原语 + 视觉映射），再谈落地。

## 八、九步工作流 → 系统映射（2026-09-18 用户给出）

> 用户原话：「明确目的 → 收集数据 → 选图型 → 搭结构 → 定规范 → 画草图 → 正式绘制 → 校验 → 导出交付」

| # | 用户步骤 | 系统对应物 | 现状 |
|---|---|---|---|
| 1 | 明确目的 | 意图理解（需求 → 要画什么） | ⚠️ 有但薄：原话直接塞给 LLM，没有「先确认意图 / 图型」的动作 |
| 2 | 收集数据 | 上下文收集（当前场景 / 用户文档 / 知识） | ⚠️ 只有当前场景；文档知识属 S2（M2 RAG） |
| 3 | **选图型** | 图型判定 + 该图型的语法约束 | ❌ **完全缺失** —— 这是「复杂图画不出」的直接原因（见第七节、`docs/diagram-grammar.md`） |
| 4 | **搭结构** | 排版：模块 → 成员 → 模块间关系 | ❌ 缺失（S1b / v2-39，已立项待审） |
| 5 | 定规范 | 契约 + 语义→视觉映射表 | ⚠️ 契约有但太窄（S1a / v2-40）；映射表缺失 |
| 6 | 画草图 | LLM 首轮生成（坐标只是种子） | ✅ 有 |
| 7 | 正式绘制 | 布局引擎（ELK 竖排）+ 几何求解 | ✅ 有（S1 闭合，v2-38） |
| 8 | 校验 | `GraphValidator` + 失败重试 | ⚠️ 有，但 issue 明细不外露（只报数量 → 白耗一整轮，约 130 秒） |
| 9 | 导出交付 | 画布渲染 + 导出 | ⚠️ 渲染有；导出（PNG/SVG）由 Excalidraw 内置但**未验证**，且没有「交付」概念（分享 / 快照） |
