# diagram-grammar.md — 图型语法与元素能力矩阵

> 只回答一个问题：**我们要支持哪些图型、每种图型需要什么表达能力、现在缺什么。**
>
> 定位：这是九步工作流里「**定规范**」的底座 —— 契约该有哪些字段，由这里的图型语法**反推**，
> 而不是看渲染器有什么就顺手加什么（那样只会得到一份更长的形状清单，不是语法）。

## 一、为什么必须有这一层（2026-09-18 结论）

用户给出的九步工作流：

> 明确目的 → 收集数据 → **选图型** → 搭结构 → 定规范 → 画草图 → 正式绘制 → 校验 → 导出交付

映射到现有链路（详见 `../plans/masterPlan/roadmap.md` 第八节）后，「**选图型**」是**唯一完全不存在**的一环。

后果（这是"画不了复杂图形"的根因，不是渲染器不行）：

- 契约现有的 7 种 `type` 是一份**形状清单**（矩形/圆/菱形/箭头/线/文本/画框），不是**图型语法**。
  形状清单只回答"能画哪些几何体"，回答不了"时序图该怎么组织"。
- LLM 拿到形状清单后，对任何图型都只能**硬凑**：题 4 时序图被硬凑成 `text + arrow + frame`（26 个 text 互叠 72 对），
  题 8 甘特图必然同族翻车 —— 因为"生命线""时间条"这两种语义在契约里没有对应物，LLM 只能猜。
- **所以只扩字段也不够，只跑测试更不够**：不知道"要支持哪些图型"，就无法判断契约扩够了没有。
  测试只能暴露症状，不能定义需求空间。

## 二、元素能力矩阵（Excalidraw 0.18.1 实测 vs 契约）

实测方法：探针 `../tools/e2e/probe_contract_capacity.py`（走 Vite dev server 动态 import 官方转换器
`convertToExcalidrawElements`，**不调大模型、不调后端**），截图
`.playwright/shots/probe-contract-capacity.png`。

| 能力 | Excalidraw 0.18.1 | 契约 | 后果 |
|---|---|---|---|
| 元素类型 | **10 类** | **6 类可用** | 缺 image / iframe / embeddable / magicframe；`freedraw` 前端丢弃 + 提示词禁用，等于没有 |
| **箭头端点形状** | **12 种**（含 3 种数据库鸦脚） | **0**（连字段都没有） | **ER 图基数（1:N）、聚合/组合、阻断（bar）全画不了** |
| **逻辑分组** | `groupIds`，**支持多层嵌套** | ❌ 没有 | **没有"模块"概念** → v2-39 排版无处落地 |
| **空间容器归属** | `frame.children` → 反填成员 `frameId` | ⚠️ 有 frame，但 children 被补空 | **画框与内容零关系**（实测见第四节） |
| **frame 嵌套** | ✅ 转换器接受（`innerFrameId='outer'`） | ❌ 无从表达 | 架构图「外层模块 → 内层子系统」表达断裂 |
| 图形虚线 | ✅（`strokeStyle` 在基类） | ❌ 只有 arrow / line 有 | 分组边界、模块轮廓、生命周期线都画不了虚线 |
| 圆角 | ✅ `roundness` {1,2,3} | ❌ | 无法用视觉区分"步骤 / 系统 / 模块"层级 |
| 填充图案 | 4 种（hachure / cross-hatch / solid / **zigzag**） | 3 种 | 少一个 |
| 文本垂直对齐 | ✅ `verticalAlign` | ❌ | 生命线顶端标签、泳道标题无法对齐 |
| 文本自适应 | ✅ `autoResize` | ❌ | 长文本只能撑宽，不能换行成块 |
| 字体 | **8 种 + 2 fallback** | 3 种（1/2/3） | 够用，但"标题 vs 正文"缺区分手段 |
| 超链接 | ✅ `link` | ❌ | 图不能当导航入口 |
| 锁定 | ✅ `locked` | ❌ | — |
| **折线（多段）** | ✅ points 多段（不绑定即可） | ✅ 已有 `points` | **可用** —— 探针渲染出 3 段折线（推翻"折线画不了"的旧结论） |
| 绑定箭头 + 端点形状 | ✅ 可共存（实测 `endBinding` 与 `crowfoot_many` 同时成立） | ❌ | 有向关系上也能带鸦脚 —— ER 图的关键前提 |
| 保留自定义 id | ✅ `regenerateIds: false` | —（前端靠 `customData` 认领） | 可用于稳定回写键，非必需 |

**一句话**：契约把一份表达能力很强的格式，砍成了"6 种形状 + 约 30 个字段"。
**这不是渲染器的限制，是契约自己画的圈。**

## 三、图型清单（源自 `./复杂提示词测试集.md` 的 9 条）

9 条题里 **8 条带"嵌套"** —— 这是当前契约最缺的能力。

| # | 图型 | 语法三要素（节点 / 边 / 容器） | 需要的、当前没有的能力 | 现状 |
|---|---|---|---|---|
| 1 | 架构图（多层嵌套） | 组件 / 调用与协议 / **多层模块** | `groupIds` 多层嵌套、`frame` 嵌套、组件圆角与配色层级 | ❌ 只能画成扁平一堆框 |
| 2 | 流程图（嵌套子流程） | 步骤与判定 / 流转 / **子流程** | `groupIds`、判定分支标签避让 | ⚠️ 能画，元素爆炸（实测 143 个） |
| 3 | 状态机（嵌套状态） | 状态 / 迁移 / **复合状态** | `groupIds` 嵌套、初始/终态视觉、迁移条件 | ❌ 复合状态无表达 |
| 4 | 时序图（嵌套循环） | 参与者 / 消息 / **片段(loop/alt)** | 生命线（虚线 line）、`verticalAlign`、消息箭头形状、片段框 | ❌ **布局整体跳过**（无图形元素） |
| 5 | 数据流图（多层嵌套+反馈） | 处理 / 数据流 / **数据存储与边界** | `strokeStyle` 虚线（边界）、反馈环路 | ❌ 边界画不出 |
| 6 | 部署图（嵌套集群） | 节点与实例 / 网络连接 / **集群与命名空间** | `groupIds` 嵌套、容器虚线框 | ❌ 集群无表达 |
| 7 | 决策树（嵌套决策） | 判定 / 分支 / **子决策组** | 分支标签避让、组嵌套 | ⚠️ 能画，标签压叠 |
| 8 | 甘特图（嵌套任务） | 任务条 / 依赖 / **时间轴与阶段** | **没有"条"这个原语**（可用圆角矩形近似）、时间轴刻度 | ❌ 无对应图型 |
| 9 | 结合图（流程+架构+统计） | 多图型混排 / — | 分区（frame）+ 每区独立布局 | ❌ |

**归纳出的四类硬需求**（契约扩展的真正依据）：

1. **层次/嵌套**（8/9 条）→ `groupIds`（多层）+ `frame`（空间容器，可嵌套）
2. **关系语义**（全部）→ 箭头端点形状 + 线型（实/虚/点）区分依赖、数据流、异步、基数
3. **非图形图型**（时序图、甘特图）→ 必须让布局对"没有图形元素"的图也生效
4. **分区布局**（架构图、结合图）→ 模块间留通道，是 v2-39 排版的输入

## 四、本次实测推翻/修正的三条旧结论

### 4.1 `frame.children` 不是"渲染器实现细节、无语义"（**修正用户 09-17 拍板的方案 a 的落法**）

对照实验（`children` 正确 vs 空）：

| 输入 | n1 的 `frameId` | n2 的 `frameId` |
|---|---|---|
| `children: ['n1','n2']` | **`fA`（归属建立）** | **`fA`** |
| `children: []`（**当前行为**） | `null` | `null` |
| 完全不给 `children` | 抛 `TypeError: ...reading 'forEach'` | — |

**结论**：09-17 拍板"契约不含 children"的**动机仍然成立**（不让 LLM 乱填），
但落法错了 —— 适配层补 `children: []` 只解决了"不抛错"，**没有建立归属**：
框与内容在数据模型里毫无关系（拖框不带走内容、删框不带走内容、框也不会因内容变化而调整）。

正确落法：**children 由后端按几何/分组关系算出，适配层填进去，LLM 依旧不碰它**。
（转换后 frame 元素上没有 `children` 字段，归属只体现在成员元素的 `frameId` 上。）

### 4.2 折线不是"不可行"，而是"绑定后不可行"

之前结论"绑定箭头 ⇔ 直线"**只对绑定成立**。探针实测：**不绑定 + 多段 `points` → 折线正常渲染**
（截图里 3 段虚线折线、3 点箭头都在）。也就是说"线条不只是直线"这一步**没有技术障碍**，
缺的是后端算路径 + 拖动后的重新路由（见 roadmap 第九节）。

### 4.3 鸦脚与绑定可以共存

实测 `endArrowhead: 'crowfoot_many'` 与 `startBinding` / `endBinding` 同时成立。
**ER 图的基数标记不必以"放弃绑定"为代价** —— 之前认为"要端点形状就得解绑"是错的。

## 五、结论

1. **契约要按"图型语法"扩展，不按"渲染器字段"扩展。** 字段是手段，语法是目的。
2. **扩展的第一优先级是"层次"**（`groupIds` 多层 + `frame` 归属/嵌套）—— 8/9 条题的核心诉求，
   同时是 v2-39 排版的前置依赖。
3. **第二优先级是"关系语义"**（箭头端点形状 + 线型）—— 让"依赖 / 数据流 / 异步 / 基数"可区分。
4. **第三优先级是"非图形图型"**（时序/甘特）—— 属布局侧改动，不必等契约。
5. 契约扩展计划见 `../plans/underway/v2-40-contract-capacity.md`。
