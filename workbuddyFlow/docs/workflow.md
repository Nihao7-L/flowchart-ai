# workflow.md — 自反馈机制

> 只回答一个问题：**系统跑起来后，怎么知道自己做得好不好，并自动修正。**
> 缺下面任一条，就是装饰。

## 一、信号源（反馈从哪来）

- **run-verify 输出**：编译/单测/前端检查通过率（每次执行必跑）。
- **graph 校验 issues**：出图结构化校验的 field/reason/hint 明细。
- **tech-debt-tracker**：产品内 Agent（ReAct/工具/校验/会话）出错的回收池。
- **用户显式反馈**：聊天中对"图不好看/换复杂的"等指令即修正信号。
- **人工抽检**：人读 `activeLog.md` 复盘执行质量。
- （规划中）**评测集打分**：固定用例集每次改动前后跑，比对通过率/成本——当前未建，见第五节。

## 二、判断标准与阈值（什么算好/差，必须有数值）

| 指标 | 好 | 差（触发动作） |
|---|---|---|
| run-verify 退出码 | 0（VERIFY PASS） | 非 0（VERIFY FAIL）→ 自动修 |
| 单次出图校验轮数 | ≤1 轮通过 | ≥3 轮仍不通过 → 升级人工/记 tech-debt |
| 图 JSON 契约符合度 | 100% 字段合法 | 任一 field 非法 → 带 issues 重试 |
| token 单会话成本 | ≤ 预算阈值 | 超阈值 → 降级小模型/截断 |
| 缺陷回收率 | tech-debt 全部升格路线图 | 长期滞留 tech-debt → 阶段收尾扫 |

> 注：延迟 P99/QPS、单测覆盖率等量化阈值当前**未埋点**，列为待建（infra 阶段 v2-27+）。

## 三、触发动作（偏差出现后干什么）

- **自动重试**：校验不过 → 带 issues 重调 LLM，≤3 轮（闭环自动，不問人）。
- **自动修**：run-verify FAIL → Agent 看输出自改，不阻断用户。
- **降级**：token 超阈值 / LLM 超时 → 降级小模型或返回部分结果。
- **写回知识库**：产品 Agent 缺陷 → 记 `tech-debt-tracker.md`，可升格路线图任务。
- **告警给人**：重大越界（如 Agent 误改 env/系统设置）→ 立即告警用户，不自动处理。

## 四、消费者（给人看，还是驱动程序自调）

- **自动闭环（程序自调）**：校验重试、run-verify 自修、token 降级——无需人介入。
- **人审（给人看）**：`activeLog.md`（执行证据）、`tech-debt-tracker.md`（欠债）、run-verify 报告——由用户评审与决策升格。
- 设计原则：能自动的自动，需判断的交人；所有自动动作留痕供人回溯。

## 五、闭环节奏与效果度量

- **节奏**：每次执行 → 必跑 run-verify + 追加 `activeLog.md` 一行（带证据）；每阶段收尾 → 扫 `tech-debt-tracker.md` 决定修或升格；（规划）评测集 → 每次代码改动前后跑同一批固定用例。
- **效果度量（当前可量化项）**：verify 绿率（PASS/总执行）、校验平均轮数（越低越好）、缺陷回收数（tech-debt → 路线图升格数）。
- **已知缺口**：无独立评测集/回归基线、无运行时指标埋点——闭环目前**偏人工外置记忆**，非系统级自动学习。这是 v2-3（验证）/ v2-27（可观测）要补的。

## 六、与评测集 + 回归测试绑定（硬要求）

每次改动前后跑同一批固定用例，比对**通过率**与**成本**。没有度量，闭环就只是流程图上的一个圈。当前状态：评测集待建（v2-3 起），先以 run-verify + activeLog 做最小闭环。
