## 背景（为什么现在做）

- `architecture.md` 2.4 包表把**「布局」明确划归 `graph/`**；ADR-4 写明"**坐标由布局算法确定性生成、作为数据存进 IR**"。
- `scene.schema.json` 第 5 行（契约自述）写着"坐标为数据：**生成时由布局算法确定性算出**"。
- `m6a-render.md` 把 `layout` 列为 v2-24a 交付项（勾选至今为空），并注明"坐标由 IR 携带、**后端布局生成**；前端 `layout` 仅兜底增量"。
- **但实现侧没有它**：`GenerationService` 流水线 = LLM → `SceneBinder` → `SceneDeduper` → `GraphValidator` → 下发，**无布局环节**；全仓 `layout` 只命中 3 处注释。
- 连带后果：`PromptService` 第 87 行反向告知 LLM"给出合理排布即可，**后续会被布局对齐**"——把布局责任推给模型，而那个"后续"不存在。
- v2-23 设计稿把它列为"从 PoC 原型继承的不变项"，但**该 PoC 不在 git 历史里**（全 rev 搜 `buildSkeletons` / `syncPositions` / `layout(` 均无命中）→ 只能重写，捡不回来。

## 目标

把"摆在哪"从 LLM 手里收回，由后端确定性算出。新增 `graph/SceneLayout`（分层布局）插入生成流水线，使**任意**合法 IR 经它之后都满足：**无重叠 / 边不过短 / 带标签的边装得下标签 / 纵横比受控 / 同输入同输出**。

**两种模式（2026-09-17 新增 —— A1b 落地后这已是硬约束）**：① **新建**（会话里没有既有 model）→ 全量重排，这正是本步要治的"乱"；② **编辑**（有既有 model）→ **保留未改动元素的坐标，只给本次新增的元素定位**。理由：`PromptService` 已向 LLM 承诺"没有要求改动的元素必须原样保留 id / type / 几何"，而这条承诺已由 v2-37 的 `graph/SceneDrift` 变成**会拦人的校验** —— 编辑模式下若整图重排，会被判为"整图重排"并进修正轮。

量化验收（缺一条不算完成）：布局后两两图形包围盒**零重叠**；含标签的箭头**可见长度 ≥ 标签宽度 + 2×内边距**。

## 边界

- **允许新增**：`graph/` 下的布局类（`SceneLayout` + 私有小工具）、几何校验（并入 `GraphValidator` 的 `checkGeometry`）、对应单测
- **允许修改**：`service/GenerationService`（插一步 + 修超时兜底 + 首轮通过即发）、`service/PromptService`（坐标语义 + 元素上限）、`graph/GraphValidator`（补几何 issue）
- **禁止改动**：`frontend/`（本步完全不碰 —— 前端兜底布局已按 2026-09-17 决定 A2 **删除**，前端只消费后端给的坐标）、`llm/`、`session/`、`controller/` 的接口签名（`/api/chat` 事件协议不变）、`scene.schema.json` 的必填字段集（见下方"契约口径"说明）

### 决策 1：不新增依赖，手写分层布局（2026-09-17 已拍板：按推荐执行）

ADR-4 备注"质量依赖 elkjs/dagre"，但本步**不引入**：

1. 项目先例是**手写**（`GraphValidator` 弃 networknt），风格一致；
2. 引 Maven 依赖会触发网络下载 —— 按协作红线须**另行征得同意**；
3. 本步要解决的是"别乱、边别太短、别盖线"，分层布局（layered / Sugiyama 简化版）手写完全够用。

代价：布局质量弱于 ELK（不做多轮交叉最小化、不做节点内换行）。若将来要升级，按 ADR-4 修订另开计划 —— 届时需明确"ELK 是 Java 库还是 JS 侧"，因为 ADR-4 原文只写了 elkjs（JS）。

### 决策 2：不改契约的必填字段集（2026-09-17 已拍板：按推荐执行）

`shape` 分支目前 `required: [id, type, x, y, width, height]`。**保持不动** —— 改了要同步 prompt、校验器、前端适配层与契约测试，收益只是"省几个 token"，不划算。改为只在 **prompt 文案**里说明"坐标会被后端重算，可给近似值"。

### 决策 3：布局分「新建 / 编辑」两种模式（2026-09-17 已拍板）

- **新建**（无既有 model）：整图全量重排。
- **编辑**（有既有 model）：**只给新增元素定位，未改动元素的坐标原样保留**。
- 为什么这是硬约束而非优化：`PromptService` 已承诺"没有要求改动的元素必须原样保留 id/type/几何"，v2-37 的 `graph/SceneDrift` 已把这条承诺**变成可执行的校验**（编辑语境首轮，可比元素漂移 ≥3 个且占比 ≥50% 即判"整图重排"→ 进修正轮）。若本步不分模式，编辑时"改个颜色"就会触发刚建好的校验，形成**布局与校验互相打架**。
- 实现口径：`SceneLayout` 需要知道"哪些元素是新增的"（由 `GenerationService` 传上一版 id 全集求差即可），只对新增元素跑分层 + 与既有元素做一次重叠消解；既有元素坐标**一个都不动**（整体平移也放过，见 `SceneDrift.isUniformTranslation`）。

## 分层边界

落在 `graph/`，由 `service/` 调用 —— 与包表箭头方向一致（`service/` → `graph/`，`graph/` 不调任何人）。不触碰 `rag/` `tools/` `agent/`（后续阶段）。原因：布局是"把语义 IR 变成带坐标 IR"的纯计算，天然属于图的处理，且必须对 M1 与将来的 Agent 改图**共用一份**（否则两条路各排一次，用户会看到图反复跳）。

## 前置

无。布局是纯函数，单测不需要起 Spring 容器、不需要 LLM。

## 步骤

1. **`SceneLayout`：分层**。建邻接（只用**两端都绑定的 arrow** 作为有向边）→ 入度 0 的点做根 → 最长路径分层（避免 BFS 的"层号抖动"），环/自环打断（复用 D3 的自环识别结论，环上的点统一放一个层）。
2. **层内排序**：按父节点重心（barycenter，即父节点平均 x）排序，一趟向下 + 一趟向上，减少连线交叉。
3. **坐标分配**：层 → 主方向（默认自上而下；当层数 > 6 或主方向宽度超阈值时切**自左而右**，避免"竖长条"）；层内按序分配副方向坐标，**统一节点尺寸**（同类型同尺寸）；**强制最小间距**（水平 ≥ 220px / 垂直 ≥ 120px，抽成常量便于调）。
4. **重叠消解**：逐对检测包围盒相交，沿副方向推开（保序、不破坏层结构）。
5. **网格对齐**：所有坐标吸附到 20px 网格（治"歪歪扭扭"，也让快照测试稳定）。
6. **保证边可见长度**：对每条边算两端边界交点距离；**含标签的边**要求 `长度 ≥ 标签估算宽度 + 2×内边距`（标签宽度按"字符数 × fontSize × 0.6 + 内边距"估，中文按 1.0 em 更保守），不满足就加大该层间距后重跑步骤 3~5。
7. **纵横比约束**：布局完成后若 `宽高比 ∉ [0.5, 2.0]`，整图换主方向重排一次（只换一次，防止死循环）。**这一步同时关闭 `v2-24a-canvas-embed.md` 第 154 行的遗留**（"竖长条 729×2130、zoom 掉到 0.2"）。
8. **`GraphValidator` 补 `checkGeometry`**：图形重叠 / 边过短 / 标签宽 > 边长 三类 → `ValidationIssue(field, reason, hint)`，进修正循环。
9. **`GenerationService` 接线**：`LLM → bind → dedup → **layout** → validate`；顺序理由：布局要在绑定制箭头之后（才能按"哪两个图形相连"分层），在去重之后（别为将被删的线排版）。**布局要分两种模式**（见决策 3）：编辑模式只给新增元素定位，未改动元素的坐标必须**原样带过**，否则会被 v2-37 的 `SceneDrift` 拦下。
10. ~~修超时兜底漏洞（补第三条兜底：有存档就发存档）~~ **【2026-09-17 修订：本步作废，改为从构造上消除该漏洞】** 原诊断（"第 1 轮已通过、第 2 轮超时 → 合格结果被白丢"）成立，但它**只存在于"通过后仍空跑两轮"这个自己制造的风险里**。步骤 11 落地后（校验 0 issue 立即发出）不存在"已合格还要再跑一轮"的情形，第三条兜底**没有触发路径**；且 `lastGoodJson` 在通过即发后恒为 null，属**不可测的死代码**。故按"不留死代码"处理：**删除** `lastGoodJson` 及其 3 处存档分支（已随 A3 落地），而不是新增。⚠️ **勿照本条旧文字复推。**
11. **首轮通过即发（治超时的一半）**【✅ 2026-09-17 已随 A3 落地】：原策略是"校验通过仍 `continue` 再跑"直到跑满 3 轮；而**第 2 轮用的 prompt 与第 1 轮完全相同**（通过时不会构建修正 prompt），等于靠采样随机性重摇一次，代价是把用户等待时间直接 ×3 —— 59 元素单轮近 300 秒时，这就是"必然超时"的来源。已改为**首轮通过即发**（保留"有 issue 才继续修正轮"的既有语义）。证据：`state/activeLog/2026-09-17.md` 的 17:00 条（`GenerationServiceTest` 同步断言 LLM 调用次数，全绿）。
12. **`PromptService`**：① 第 87 行改成真话（"坐标可给近似值，后端会按拓扑重算"）；② 加**元素数量上限**（建议 40，抽常量），并要求超限时**先给纲要再分次生成**，而不是硬吐 60 个元素；③ 明确"连线一律 arrow 绑定"等既有规则不动。
13. **测试**：见下表；含确定性快照测试。

## 验收口径

1. 布局后**两两图形包围盒零重叠**（容差 0，网格对齐后是整数比较）
2. 每条两端绑定的箭头：两端端点落在各自图形**边界**上，且**可见长度 ≥ 60px**
3. 含标签的箭头：**边长度 ≥ 标签估算宽度 + 2×内边距**（治"加文字就看不到线"）
4. **确定性**：同输入跑两次，输出**字节级一致**（可快照断言）
5. 图的长宽比 ∈ **[0.5, 2.0]**（同时关闭 v2-24a:154 遗留）
6. ~~超时兜底：第 2 轮抛异常仍发存档~~ **【已作废】** 首轮通过即发后不存在后继轮次，"存档"机制已删。改判：LLM 抛异常时 SSE 必须收到**带原因的** `error`，且通道正常收尾（不留悬挂连接、不刷 `Exception in thread`）
7. **首轮通过即发**【✅ 已达成】：校验 0 issue 时只调 1 次 LLM（`GenerationServiceTest` 用打桩 Provider 断言调用次数）
8. 后端 `mvn clean test` 全绿 + `checkstyle:check` 0 违规；前端三绿（本步不改前端，做回归确认）
9. 真实 LLM 端到端：用 2026-09-17 那句"电商系统微服务架构图"复跑，肉眼可读（不重叠、箭头可见、标签不盖线）
10. **两种布局模式**：新建 → 全量重排；编辑 → **未改动元素的 `x/y/width/height` 与上一版完全一致**，且 `SceneDrift` 不报 issue（这条是 A1b 与 v2-36 的**联锁验收**，缺它则两个交付项会互相打架）
