状态机 = 若干**状态** + 状态之间由**事件**触发的转换。

- **必须声明 `diagramType:"state-machine"`**。
- 状态是名词（待支付 / 已发货 / 已取消），画成圆角意象的矩形或椭圆；**转换是带事件名的箭头**，事件写在箭头上（「支付成功」「用户取消」）。
- 箭头标签写「事件」，必要时带条件：「支付成功 [库存充足]」。别把动作写在状态框里。
- 必须有一个初始状态和一个终态；初始态用一条没有起点的入边（从空白指向它），终态可以画双框意象 —— 但契约里没有双框类型，就用普通矩形并在名字里写「（终态）」。
- 自转换（某个事件后回到自己）要单独画一根回到自身的箭头并写清事件。
- 不要画成流程图：状态图没有「流程」式的单向主线。条件分支有两种合法表达：① 同一状态上多条带不同事件 / 守卫（`[条件]`）的出边；② 显式画一个**选择伪状态（菱形）**再分出带守卫的支路。优先用①，分支特别多时再用②。状态转换箭头**不写 `relation`**（用默认样式），语义靠箭头上写的事件名表达。
- 同一对状态之间若有两个方向的转换，各画一根，不要合成双向一根。

## 组合态（状态里还装着一台状态机）

需求里出现「订单包含 处理中 / 已完成 / 已取消」「售后中包含 退款 / 换货 / 维修」这种**状态里还有状态**的结构时，用 `group` **路径**表达嵌套，这是状态图最容易画炸的地方：

- **子状态写从内到外的数组**：`"group": ["处理中", "订单"]` 读作「处理中，它属于订单」。
- **组合态节点自己也写同一条完整路径**（`"group": ["处理中", "订单"]`）—— 它和它的子状态才会被框进**同一个**容器框里。只给子状态写扁平字符串、组合态自己另写一个名字，后端会把内外层当成两个并排模块，中间连出贯穿整张画布的长线。
- 组合态对外仍是一个普通状态：别的状态连它，事件照写在箭头上；**跨层的深转换直接连**（外层状态 → 内层子状态），不要为了「跨框」另造中间状态。
- 嵌套最多两层（外层域 + 内层组合态）。再深就拆成两张图，别硬塞。
- **整图最外层用一个 `group` 兜住所有状态**（如 `["订单"]`、`["请假单"]`），别留一堆无 `group` 的裸状态：无分组节点会被排成独立的一块、摆到画布另一边，把图拉成一条长带子。

## 并行正交区（多台状态机同时跑）

需求里出现「同时还要发通知 / 等审核 / 同步第三方」这类**并行**语义时，把每个并行状态机各做成一个 `group`：

- 每个并行区自己一个 group（`通知` / `审核` / `同步`），用路径与主生命周期并列：`"group": ["通知", "订单"]`。
- 每个并行区**内部各自有初始态和终态**（如 待通知 → 已通知 / 通知失败）。
- **并行区之间一根箭头都不画** —— 区域之间的关系是「同时」而不是「先后」，画箭头就等于说成了顺序。
- 并行区与主生命周期之间的交互（如「待支付 → 发通知」）画一根箭头即可，不要来回连。

## 配色语义（`color`，值域 blue/green/yellow/red/purple/orange/cyan/pink/gray）

用户没有点名颜色时，按状态语义配色，让整图一眼能读出「正常 / 等待 / 异常」：

- 正常推进、可用路径 → `green`；等待中、进行中、待处理 → `yellow`。
- 异常、失败、取消、超时、退回 → `red`；终态、已完成 → `blue`。
- 并行区的状态 → `purple`；历史态、归档 → `gray`。
- 同一语义在图里**必须同色**（所有「失败」态都是 red）；用户点名了别的颜色就按用户的来。
