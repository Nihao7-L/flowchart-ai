# Token 到底是什么？为什么中文、英文、代码消耗的大模型 Token 不一样

> 很多人以为大模型按"字数"或"字符"计费，其实都不是。大模型最小的处理单位是 **Token（子词，即比单词小、比字符大的有意义片段）**。本文用大白话把 Token 的来龙去脉讲清楚，并回答一个高频疑问：同样一段内容，为什么中文比英文费 Token、代码也比散文费 Token。

---

## 一、先理清：字节、字符、Token 到底什么关系

这三个词经常被混为一谈，其实它们是**同一段文字的三种表示层级**，从上往下越来越"粗"。

- **字节（byte）**：计算机只认 0 和 1，8 个 0/1 打包成 1 个字节，能表示 256 种值。硬盘、内存里**一切都是字节**，没有"字"的概念。
- **字符（character）**：人眼看到的符号，比如 `A`、`你`、`😊`。计算机不认识"你"，它只认识数字，所以必须靠一张**编码表（encoding，把数字翻译成文字的规则，如 UTF-8）**把数字还原成字符。
  - 英文 `A` = 数字 65，存 **1 个字节**
  - 中文 `你` = 数字 20320，存 **3 个字节**（1 个字节装不下几万个汉字）
  - emoji `😊` 存 **4 个字节**
  - 所以：**1 个字符 = 1~4 个字节**，取决于是什么字、用什么编码。字节是底层存储形态，字符是上层显示形态。
- **Token（子词）**：分词器（tokenizer，把文字切成模型能懂的数字的工具）按出现频率，把常挨在一起的字符**打包**成一个"词表条目"。模型从头到尾只认 Token 对应的整数编号（ID），不认识"字"也不认识"字节"。

一句话定位：

| 层     | 视角           | 比喻                 |
| ----- | ------------ | ------------------ |
| 字节    | 计算机存储层       | 快递的一个个螺丝零件         |
| 字符    | 人能读层（编码还原）   | 你写下的一个个汉字          |
| Token | 模型处理层（按频率打包） | 快递公司把常发组合预装好的"标准箱" |

## 二、Token 是怎么来的？为什么不用字符 / 字节 / 单词

最早 NLP 用**单词级**（word2vec 时代），按空格切词，简单但有**未登录词（OOV，即训练时没见过的词）**死穴：新词、拼写错误、专业术语直接懵。

为了解决 OOV，**子词（subword）**登场：把词拆成常见部件，比如 `unforgettable` → `un` + `forget` + `table`，生词也能用部件拼出来。

主流做法是 **BPE（字节对编码，从最小单位往上反复合并高频组合成词的算法）**：

1. 从一个字符 / 一个字节开始；
2. 统计"哪两个相邻单元最常一起出现"，把它俩合并成一个新单元；
3. 反复合并，直到词表达到目标大小（GPT 约 10 万，Claude 类似）；
4. 高频词保留整词（`the` = 1 个 Token），低频词拆成部件（`Transformer` 可能拆成 `Trans` + `former`）。

那为什么不用更"直觉"的单位？

- **不用字符**：序列太长。Transformer 的注意力机制（模型理解上下文关系的关键计算）计算量**随序列长度平方增长**（长度翻倍，计算量约翻 4 倍）。字符级下"你好世界"是 4 步，模型要一步步看，又慢又难抓远距离关系，且单字几乎不带语义。
- **不用字节**：UTF-8 下中文 = 3 字节、emoji = 4 字节，等于把中文又打回更碎的层面，和字符级是同一类毛病，还完全丢失了"字"的语义边界。
- **不用单词**：装不下未登录词，且中英文日没统一空格边界，一套单词表覆盖不了多语言。

**结论**：Token 是三者的甜点——比字符/字节"粗"（序列短、算得快），比单词"细"（能拼出任意新词）。

## 三、一次调用里，Token 在哪儿变成数字？是谁干的？

这是最容易搞混的一点。以 OpenAI 兼容协议（请求/响应 JSON 长成 OpenAI 规定样子的协议）为例：

你本地（比如一个 Spring Boot 应用）干的事只有：

1. 把系统提示词 + 用户输入拼成一个**文字字符串**；
2. 把它塞进 HTTP 请求体的 `messages[].content` 字段；
3. 发 POST 给模型供应商；
4. 收到响应 JSON，取出 `content` 里的文字交给解析逻辑。

**你本地从头到尾只有"文字"在进出，没有 Token，也没有编码。**

真正把文字变成 ID 的，是**供应商的 GPU 服务器**：

| 环节               | 在哪干        | 干什么                    |
| ---------------- | ---------- | ---------------------- |
| 拼 prompt         | 你本地        | 文字字符串                  |
| 发 HTTP           | 你本地        | 把文字放进 JSON 发走          |
| 文字 → Token → ID  | **供应商服务器** | 用模型的 tokenizer 编码      |
| Transformer 矩阵运算 | **供应商服务器** | 算                      |
| ID → 文字          | **供应商服务器** | detokenize（解码，把数字拼回文字） |
| 返回文字             | **供应商服务器** | 塞进 JSON 的 content      |
| 解析               | 你本地        | 提取结构                   |

为什么协议设计成"客户端发文字、服务端 tokenize"？因为**不同模型的 tokenizer 不一样**——MiMo 的切词规则和 GPT 不同，词表也不同。如果让你本地先 tokenize 再发，你得装对应 tokenizer 且版本对齐，换模型就废。所以供应商统一在自己服务器上 tokenize，客户端只管发文字。

**代价**：计费按供应商 tokenize 后的 ID 数算。你发一段中文 prompt，本地只是字符串，供应商数完 Token 才扣费。

## 四、模型内部"算"的到底是什么？

常有人说"模型做纯整数运算"——这不严谨。**整数 ID 只在两端出现，中间全是浮点（小数）运算**：

1. **Embedding（词嵌入，拿 ID 查一张巨大的"意思表"把 token 变成一串浮点数的操作）**：ID `123` 查表变成 `[0.21, -1.03, 0.87, ...]` 共 4096 个小数。这一步之后模型里就再没整数了。
2. **注意力层（attention，让每个词根据和其他词的相关性强弱来吸收信息的机制）**：每个向量和"提问/回答/值"三套小矩阵相乘，算相关性，把相关信息揉进来。
3. **前馈层（feed-forward，每个词再过两层矩阵乘 + 激活函数提炼特征）**：又是两次矩阵乘。
4. **重复 2+3 几十层**（模型有几十层，每层参数不同）。
5. **输出层**：当前向量 × 一张超大矩阵（维度 × 词表大小），得到每个候选词一个分数。
6. **Softmax（把一串分数压成 0~1 概率、加起来=1 的函数）**：分数变概率。
7. **采样（按概率随机挑一个词，temperature 控制随机程度）**：挑出下一个 Token 的 ID。
8. 把新 ID 拼到序列末尾，**从头循环**直到输出"结束"标记。

一句话比喻：你的话变成一串坐标，模型拿一本几十亿个数字的"规则书（参数，模型训练学出来的数字权重）"反复加工，最后给每个候选词投票，按票数挑下一个词。

## 五、重点：为什么中文、英文、代码消耗 Token 不一样

根因只有一句：**Token 按"词表里怎么切"算钱，不是按字符数算；中英文 / 代码的切法不同**。

- **英文省**：有空格词边界，BPE 把高频组合合并成整词。`hello` = 1 Token，约 **1 Token ≈ 4 字符**。
- **中文费**：无空格分词，汉字本身已是最小语义单位，没法像 `un+forget` 那样拼。BPE 在中文上合并收益极低，基本**一字一 Token**，约 **1 Token ≈ 1~1.5 个中文字**。
- **代码费**：关键字、括号、缩进、运算符各自独立成 Token（`def foo(x):` 常拆成 `def` ` foo` `(` `x` `):` 多个），语义密度低。约 **1 Token ≈ 2~3 字符**，和中文接近。

直观对比（同样约 100 个字符）：

| 内容                                      | 大约 Token 数 | 相对成本   |
| --------------------------------------- | ---------- | ------ |
| 英文散文 "Please draw a login flowchart..." | ~25        | 1×     |
| 中文 "请画一个登录流程图，包含输入密码和验证步骤"              | ~50-70     | 2-3×   |
| 代码 / SQL / Mermaid 片段                   | ~35-50     | 1.5-2× |

⚠️ **常见误解纠正**：不是"中文 1 字 = 3 字节（UTF-8 编码，1 个汉字存 3 个原始字节）所以费 Token"——Token 不按字节算。真实原因是**词表合并在中文上不划算，一字一 Token**。

## 六、这事儿对你做 AI 应用有什么实际影响

1. **成本**：中文 prompt 比同长度英文贵 2~3 倍，做成本统计时要心里有数。
2. **上下文 / RAG 预算**：代码型、中文型文档塞进 prompt 比散文烧 Token 更快。如果做 RAG（检索增强生成，先查资料再让模型回答），要给检索结果加**总 Token 上限 + 按相似度截断**，否则长文档会把上下文窗口撑爆、把真正该看的指令挤进"Dumb Zone（上下文用到约 40% 后模型变傻的区间）"。
3. **长上下文 vs RAG**：中文场景 Token 烧得快，更凸显"先检索几页关键证据（RAG）"比"把整本文档塞进上下文"划算——长上下文窗口不会取代 RAG，二者场景不同。

---

## 七、一句话总结

Token 是 BPE 算法把字符往上合并出的子词，既是大模型最小的计算单位也是计费单位；中文和代码比英文费 Token 纯粹是分词器切法不同（中文一字一 Token、英文整词合并），所以做 AI 应用时永远要按 Token 而不是字数来估成本、控上下文窗口。
