# AI 流程图生成器（FlowAI）— 阶段总结与规划

## 一、第一版 Demo 总结

### 1.1 定位

第一版只做一件事：**验证"自然语言 → 流程图"这条路能跑通**。

不是产品，不是正式版，就是一个 Demo——证明技术链路可行，后面才有继续投入的意义。

### 1.2 Demo 做了什么

```
用户输入文字 → Gemini AI 生成 JSON → PlantUML 渲染 SVG → 浏览器展示 + 下载
```

就这一条线，端到端跑通。

| 模块 | 做了什么 | 技术选型 |
|------|---------|---------|
| 后端 | 接收文字 → 拼 Prompt → 调 AI → 解析 JSON → 转 PlantUML → 渲染 SVG | Spring Boot 3.2 + Java 17 |
| AI | 文字 → 结构化 JSON | Gemini 2.0 Flash |
| 渲染 | PlantUML 源码 → SVG 图片 | PlantUML Java API |
| 前端 | 输入框 + 生成按钮 + SVG 展示 + 下载 | 原生 HTML/CSS/JS |

### 1.3 Demo 已知局限

| 问题 | 原因 |
|------|------|
| 只有 SVG 格式，没有 PNG | Demo 阶段没做 |
| AI 偶尔生成循环边导致渲染异常 | ✅ 已在 Prompt 加防循环规则，且 DiagramService 兜底 |
| 前端 SVG 不能缩放/拖拽 | 没做交互 |
| 没有用户系统、没有历史记录 | Demo 不需要 |
| 只有流程图一种类型 | Demo 只验证流程图 |

### 1.4 代码结构

```

### ✅ 19. PNG 格式输出

> **目标**：支持 SVG 和 PNG 两种格式，用户可选择下载。

**为什么做**：SVG 是矢量图，适合网页；但很多人需要 PNG 往文档里贴，Office 不支持直接插入 SVG。

**怎么做**：
- `DiagramService` 加 `renderToPng()` 方法（PlantUML `FileFormat.PNG`）
- Controller 加 `format` 参数（`svg` / `png`），默认 `svg`
- 前端加格式切换按钮
- PNG 下载 MIME type 改 `image/png`

**验收**：选择 PNG 能下载到图片，选择 SVG 不受影响。

### ✅ 20. Prompt 调优 v2

> **目标**：让 AI 输出更稳定，从"偶尔出问题"到"基本不出问题"。

**为什么做**：Demo 阶段 AI 偶尔生成循环边（如"否"分支指回已访问的节点），导致渲染出悬空线。

**怎么做**：
- Prompt 加防循环规则：
  ```
  - 流程必须是单向的，从 start 到 end，不要循环
  - 除非用户明确提到"循环""重复""回到某一步"，否则不要产生回溯边
  - decision 的两条分支最终都应到达 end
  ```
- 连续 10 次不同输入测试，确保 JSON 均能被解析
- 测试 5 个典型场景：登录流程、审批流程、订单流程、带循环的流程、短描述

**验收**：连续 10 次输入，0 次渲染异常。

## 三、第三阶段：Harness Engineering（护套工程）

### 3.1 阶段目标

第一阶段验证了「文字 → LLM → 图表」链路可行，第二阶段加了功能。但**LLM 天生不稳定**：可能返回被 ``` 围栏包住的 JSON、可能超时、可能 5xx、可能生成非法结构。

第三阶段的思路是**给 LLM 套一层"护套"（Harness）**——在 LLM 外面包一层可靠的工程化逻辑，让系统面对 LLM 的各种"不乖"表现依然稳定、可控、可度量。对应前期 README 里设计的 **LLM Gateway 六层**：

| 网关层 | 要解决的问题 | 对应任务 |
|--------|-------------|---------|
| 固定路由 | 多个模型选哪个 | 34. 多 Provider + Fallback |
| 限流 | 别把 API 打爆 | 30. 重试与退避（含限流规避） |
| Token 预算 | 一次请求花多少钱 | 31. 成本统计与审计 |
| Fallback | 主模型挂了怎么办 | 34. 多 Provider + Fallback |
| 重试 | 偶发失败怎么处理 | 30. 重试与退避 |
| 成本审计 | 花了多少要能算清 | 31. 成本统计与审计 |

同时开启 4 个新功能（New 系列），让工具从"能用的工具"变成"好用的产品"。

### ⬜ 29. Opt1 健壮 LLM 输出解析

> **目标**：LLM 返回什么"脏"格式都能解析出合法 JSON。

**为什么做**：LLM 不保证输出纯 JSON——可能用 ```json 代码围栏包住、前后夹带解释文字、或者多出未知字段。现在的 `ParserService` 遇到这些就会解析失败，用户看到报错。

**怎么做**：
- `ParserService` 加 `extractJsonText()`：剥离 ```json 围栏 → 截取首个 `{` / `[` 到对应结尾的纯净 JSON → trim
- `ObjectMapper` 配置 `FAIL_ON_UNKNOWN_PROPERTIES=false`：LLM 多输出的字段忽略，不报错
- 解析失败时返回带上下文的错误信息（原始响应 + 失败位置），便于排查

**验收**：注入带围栏 / 带前后缀文字 / 带未知字段的 JSON，均能正确解析。

---

### ⬜ 30. Opt2 重试与退避

> **目标**：LLM 偶发失败（超时 / 5xx / 限流）时自动重试，用户无感。

**为什么做**：LLM API 偶发 429（限流）、5xx、超时是常态。现在的做法是一次失败直接报错，用户体验差。

**怎么做**：
- `OpenAiCompatibleProvider` 加重试逻辑：指数退避（1s → 2s → 4s）+ 抖动（jitter），默认最多 3 次
- 只重试**可重试错误**：网络异常 / 5xx / 429（读取 `Retry-After` 头）；4xx 业务错误（Key 无效、参数错）不重试，直接失败
- 超时配置分层：连接超时 + 读取超时分开设置
- Spring Retry 或手写循环均可（教学优先手写，讲透原理）

**验收**：模拟前 2 次 503、第 3 次成功，请求最终成功且总耗时在可接受范围。

---

### ⬜ 31. Opt3 成本统计与审计

> **目标**：每次生成花了多少 token / 多少钱，可查可算。

**为什么做**：LLM 按 token 计费。现在 `OpenAiCompatibleProvider` 已经打了 `usage` 日志，但数据散落日志里没法统计。

**怎么做**：
- 定义 `UsageRecord`（时间、模型、prompt_tokens、completion_tokens、total_tokens、估算成本）
- 把 usage 从"打日志"升级为"记录对象"，存内存（`ConcurrentHashMap`）或 SQLite
- 新增 `/api/stats` 接口：返回累计请求数、总 token、估算成本（按模型单价表）
- 成本单价表配置化（`application.yml` 里配各模型每百万 token 价格）

**验收**：连续生成 5 次后调 `/api/stats`，能看到请求数、token 总量、估算成本。

---

### ⬜ 32. Opt4 输出数据校验

> **目标**：LLM 输出的结构不合法时，给出明确的修复提示而非诡异报错。

**为什么做**：现在的校验在 `ParserService` 里是"点到为止"——发现缺字段就抛异常，用户不知道哪里错了、该怎么改。

**怎么做**：
- 抽出独立的 `DataValidator`（或 `ParserService` 内方法）：按类型校验必填字段（title/start/end）、decision 出边数量、节点引用合法性
- 校验失败返回**结构化错误**：`{ field, reason, hint }` 数组，前端能展示"第 X 步缺少 end 节点，请补充"
- 校验通过的数据才进 `DiagramService` 渲染

**验收**：构造 5 种非法数据，每种都能返回具体字段和修复建议，而非笼统的"解析失败"。

---

### ⬜ 33. Opt5 Prompt 工程优化

> **目标**：从 Prompt 层面降低 LLM 出错率，解析成功率提到 95%+。

**为什么做**：解析 / 校验都是"事后补救"，Prompt 写得好才是"事前预防"。阶段二已经加过防循环规则，本阶段继续精进。

**怎么做**：
- 每个类型（flowchart / mindmap / architecture）的模板加 **few-shot 示例**：给 1 个完整的输入输出示例
- 明确输出约束：只输出 JSON、不要解释、不要 Markdown 围栏（双保险，解析层仍兜底）
- 加"自检清单"提示：生成前自问"是否有 start/end？decision 是否有两条分支？"
- 用同一组测试输入对比优化前后的解析成功率

**验收**：同一组 20 条测试输入，解析成功率不低于 95%，且非法输出类型明显减少。

### ⬜ 34. New1 多 Provider + Fallback

> **目标**：支持多家 LLM，主模型挂了自动切备用模型。

**为什么做**：现在只支持 OpenAI 兼容协议（配一个 base-url + key）。单点风险：Kimi 限流/故障时整个服务不可用。且不同模型价格/质量不同，用户想自己选。

**怎么做**：
- 配置化多 Provider：`application.yml` 支持配置多个（Kimi / DeepSeek / 通义千问 / OpenAI），每个独立 base-url + key
- `RoutingLlmProvider`（装饰器）：按配置策略选择模型（固定 / 轮询 / 权重）
- `FallbackLlmProvider`（装饰器）：主模型抛可重试错误时，按顺序切到备用模型
- 前端模型下拉框接入真实配置（阶段二只是 UI 占位）

**验收**：主 Provider 配置错误 Key，请求自动切到备用 Provider 成功返回。

---

### ⬜ 35. New2 结果缓存

> **目标**：相同输入不重复调 LLM，秒回 + 省钱。

**为什么做**：用户反复生成相似的图（改一个字重试），每次都调 LLM 花钱又慢。相同输入的结果应该直接复用。

**怎么做**：
- 缓存 key = `type + 归一化后的 text`（trim、去多余空格、可加 hash）
- 简单版：内存 `ConcurrentHashMap` + TTL（如 1 小时）；进阶版：Caffeine 缓存库
- `CachingLlmProvider`（装饰器）包在最外层：命中缓存直接返回，不调 LLM
- 缓存命中率计入 `/api/stats`，能看到省了多少钱

**验收**：同一输入连发两次，第二次响应时间显著下降，且 `/api/stats` 中缓存命中 +1。

---

### ⬜ 36. New3 对话式 Refine

> **目标**：生成后用户可以用对话继续改图，不用重头再来。

**为什么做**：现在生成一次就是最终结果，用户想"加一步"或"把流程改简单"只能重新输入整段文字。对话式修改是 AI 工具的核心体验。

**怎么做**：
- 新增 `/api/refine` 接口：接收 `{ type, originalText, svg, instruction }`
- 把「原 Prompt + 已生成的 PlantUML + 用户指令」拼成 Refine Prompt，让 LLM 输出**修改后的 PlantUML**（或新 JSON）
- 前端加"继续修改"模式：生成结果下方出现输入框，输入指令后原地刷新图表
- 需要把原始生成上下文（Prompt / 数据结构）随响应一起返回前端，便于二次请求

**验收**：生成登录流程图后输入"加一个验证码步骤"，图表原地更新且包含验证码节点。

---

### ⬜ 37. New4 Mermaid 导出

> **目标**：除了 PlantUML，支持导出 Mermaid 语法，兼容 GitHub/GitLab Markdown。

**为什么做**：GitHub / GitLab / 语雀 / 飞书都原生渲染 Mermaid，不装任何插件就能看图。PlantUML 需要装插件或走在线服务，推广成本高。

**怎么做**：
- 新增 `MermaidConverter`（或 `DiagramService` 加方法）：FlowchartData / MindmapData → Mermaid `flowchart TD` / `mindmap` 语法
- 响应里同时返回 `plantUml` 和 `mermaid` 两个字段（向后兼容）
- 前端加"复制 Mermaid"按钮；`/api/download` 支持下载 `.mmd` 文件
- 注意：架构图在 Mermaid 用 `flowchart LR` 表达组件依赖

**验收**：生成的 Mermaid 代码粘贴进 GitHub Issue / README，能正确渲染出图。
