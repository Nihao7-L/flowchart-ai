## 一、LLM 运行机制

### 1. Token 是什么？为什么中英文代码消耗不一样？

- **一句话**：Token 是模型读写文本的最小单位（不是字符、也不是单词），计费按 token 算。
- **人话**：模型不认识"字"，它把文本切成小块。英文 1 token≈4 字符；中文因为词密，1–2 字就占 1 token；代码符号多、更碎，所以同样长度代码比散文费 token。
- **你项目**：成本统计（任务31）按 token 算；中文提示词比英文贵，RAG 塞中文文档会更烧钱。

### 2. 上下文窗口是什么？越大越好吗？

- **一句话**：上下文窗口 = 模型一次"能看到"的 token 总量（输入+输出），不是越大越好。
- **人话**：窗口大=能读长文，但更贵更慢，而且文章里讲过——窗口用到约 40% 后模型开始变傻（"Dumb Zone"，即推理质量下降的区间），中间内容还容易被忽略。
- **你项目**：你 RAG 是"检索结果全塞进 prompt"，没做 token 预算（阶段六任务47 要补），长文档场景会把真正该看的指令挤出去。

### 3. Lost in the Middle（中间迷失）是什么？怎么缓解？

- **一句话**：长上下文里模型更听得进开头和结尾，中间信息容易被忽略。
- **人话**：像人读长文，首尾记得清、中间模糊。缓解：重要信息放首尾、检索结果重排序、压缩、分块。
- **你项目**：RAG 检索回来应做重排序+截断，别把关键证据堆在 prompt 中间（任务48 方向）。

### 4. Temperature / Top-P / Top-K 分别控制什么？生产怎么设？

- **一句话**：Temperature 控"随机度"（0=最稳，高=发散）；Top-P 按概率累积截断候选词；Top-K 只取概率最高的 K 个词。生产结构化输出设 T≈0 + 硬约束。
- **人话**：三个都是"模型选下一个词时有多敢冒险"。确定性任务（出 JSON、分类）把 T 设 0；创意写作（ slogan）调高。
- **你项目**：任务33 用 Structured Outputs 的 `strict:true`，本质就是逼 T≈0 + 用 Schema 掐死非法词。

### 5. 为什么 Temperature=0 输出仍可能不一致？

- **一句话**：因为并行采样、硬件浮点非确定性、batch 调度、服务商采样实现细节，近似确定 ≠ 绝对确定。
- **人话**：即使"最稳"，底层仍有微小随机源；要真一致得固定 seed + 单并发，但通常没必要。

### 6. 大模型为什么会产生幻觉？怎么缓解？

- **一句话**：幻觉 = 模型编造不存在的内容（训练数据噪声 + 概率生成 + 缺事实锚点）；缓解靠 RAG 给事实、限定边界、引用来源、人工校验。
- **人话**：模型是"接龙机器"，没见过的事实它也会顺口编。给它检索到的真文档（RAG），它就有锚点不乱编。
- **你项目**：任务38 RAG 就是给事实锚点；前端面板显示来源，让结果可溯源。

### 7. Token 预算怎么估算？输入/输出/历史/RAG 怎么取舍？

- **一句话**：预算 = 系统提示 + 历史(可压缩) + RAG 证据(按相似度截断) + 用户输入 + 预留输出；历史用摘要、RAG 只取 topK 并限 token。
- **人话**：总窗口有限，得"排座位"。不重要的历史丢掉或总结，RAG 只放最相关的几段且控制长度，长文档分块。
- **你项目**：阶段六任务47 就是给检索结果设 token 总预算 + 按相似度截断。

### 8. 长上下文会取代 RAG 吗？

- **一句话**：不互相取代。长上下文适合"整篇要通读"；RAG 适合"从海量知识里取相关片段，省 token 且可溯源"。常混合用。
- **人话**：长窗口是把整本书塞进去读；RAG 是先翻目录找相关几页。书太厚还是 RAG 省事，且能说"我引的第几页"。

## 二、API 调用工程

### 9. 大模型 API 调用的完整链路是什么？

- **一句话**：组装上下文 → 过网关(鉴权/路由/限流) → 模型推理(采样) → 流式返回(SSE) → 后端解析(JSON) → 重试/降级 → 结构化校验 → 日志追踪。
- **人话**：你发一段话，系统先拼好提示词，网关查你能不能调、调哪个模型，模型吐字，后端边收边解析成结构，出错就重试，最后记日志。
- **你项目**：`DiagramController` → `LlmProviderConfig`(多 provider) → `RagService`(检索) → `PromptService`(拼 prompt) → 流式 SSE 返回 → `ParserService`(校验)。

### 10. Streaming 为什么改善体验？能减少总耗时和成本吗？

- **一句话**：边生成边显示，首字延迟低、用户感知快；**不减少总耗时、不减少 token 成本**，但可中途取消省成本。
- **人话**：像打字机 vs 等整篇写完。总字数一样（成本一样），但用户早看到第一个字就不焦虑；用户中途停了就真省了后续 token。

### 11. SSE / WebSocket / HTTP Chunked 怎么选？

- **一句话**：SSE（服务器单向推，简单，LLM 流式最常用）；WebSocket（双向，适合真互动聊天）；Chunked（裸分块，无标准事件格式，少用）。
- **人话**：LLM 只要"服务器一直往外吐字"，SSE 够用且不复杂；要"用户和模型来回打断"才上 WebSocket。
- **你项目**：用的就是 SSE（`generateStream` 实时进度条）。

### 12. 哪些错误可重试？哪些不可重试？

- **一句话**：可重试=网络超时/连接重置(Connection reset)、429 限流、5xx 服务端错、超时；**不可重试**=401 鉴权失败、400 参数错、内容违规（重试无意义）。
- **人话**："服务器暂时抽风"能再试；"你钥匙错了/参数错了"重试一百次也白搭。
- **你项目**：`EmbeddingClient.embedBatch` 重试 Connection reset / 429 / 5xx，正是这套分类。

### 13. 为什么大模型调用必须做幂等（idempotent，即同请求多次执行结果一致）？

- **一句话**：重试怕产生重复副作用（重复扣费、重复写库）；靠 client 去重/缓存、业务侧 request_id 去重。
- **人话**：网络抖动了你重试一次，不能让用户被扣两次钱。LLM 生成本身不幂等，得在"调用入口/业务落地"处保证。
- **你项目**：缓存命中直接返回不重复调 LLM（阶段三缓存任务），就是一种幂等/去重。

### 14. 限流为什么不能只按 QPS（每秒请求数）？

- **一句话**：大模型限流看 **RPM（每分钟请求数）+ TPM（每分钟 token 数）** 两个维度，TPM 更关键（请求大小差异巨大）。
- **人话**：一个请求可能 100 token 也可能 10000 token，只限"次数"会被一个大请求打爆；得限"总 token 量"。
- **你项目**：阶段六任务50（LLM Gateway 内化）要落地 RPM+TPM 双限流。

### 15. 模型网关（Gateway，统一收口所有模型调用的中间层）承担什么能力？

- **一句话**：路由(按任务选模型) + 限流(RPM/TPM) + token 预算 + fallback(主挂切备用) + retry + 审计(日志/成本) + 统一鉴权。
- **人话**：所有模型调用先过网关，网关决定调谁、限多少、挂了换谁、花了多少钱都记着。
- **你项目**：你已有 `LlmProviderConfig` 多 provider + 任务34 fallback，阶段六任务50 把它收口成完整 Gateway。

### 16. 调用日志里至少记哪些字段？

- **一句话**：request_id、provider/model、耗时、输入 token、输出 token、总成本、错误码、是否重试、是否缓存命中、user/session id。
- **人话**：出了问题能复盘"这次调的谁、花多少、错在哪、是不是重试救回来的"。
- **你项目**：`progressLogs` 记了 provider/token，但缺 request_id 和完整 trace（任务51 可观测性要补）。

### 17. JSON Mode 和 Structured Outputs 区别？

- **一句话**：JSON Mode 只保证"输出是合法 JSON 格式"，字段不保证；Structured Outputs 按 JSON Schema **强制字段类型和必填**（模型用约束解码，如 CFG 语法约束，生成时掐死非法 token）。
- **人话**：JSON Mode="我保证给你个能解析的 JSON，但里面有没有你想要的字段我不管"；Structured Outputs="按你给的表格严格填，缺字段/类型错我当场重来"。
- **你项目**：任务33 用 `strict:true` = Structured Outputs，字段约束从 prompt 自然语言前移到 Schema。

## 三、结构化输出与工具调用

### 18. 为什么只写"请返回 JSON"不可靠？

- **一句话**：模型可能输出多余文字、用 markdown 代码块包裹、字段缺失、类型错；必须靠 JSON Mode/Structured Outputs + 后端校验。
- **人话**：你嘴上说"返回 JSON"，模型可能回"好的，这是你要的：`json {...}`"，后端解析就炸。
- **你项目**：`ParserService` 做字段校验 + 任务33 Schema 硬约束，双保险。

### 19. Function Calling（工具调用，让模型决定调哪个函数并填参数）完整链路？

- **一句话**：模型返回 `tool_calls`(函数名+参数 JSON) → 后端执行函数 → 结果回传模型 → 模型生成最终答案（可多轮）。 
- **人话**：模型说"我要调查天气函数，参数是北京"，你真去查，把结果告诉它，它再组织成自然语言。
- **你项目**：阶段四任务39（Tool Calling）规划中，尚未实现。

### 20. Function Calling 和 MCP（模型上下文协议，工具接入标准）区别？

- **一句话**：FC 是"模型调工具的机制"；MCP 是"工具怎么被统一描述/接入的协议"。FC 可以调用 MCP 暴露的工具。
- **人话**：FC 是"打电话的动作"，MCP 是"电话簿标准格式"，让不同工具都能被同一套方式调。

### 21. MCP Tool 和普通 HTTP API 关系？

- **一句话**：MCP Tool 把普通 HTTP API 包成"模型能理解的标准工具"（带描述+输入 schema+输出），本质还是调 API，只是加了模型友好封装。
- **人话**：你本来有个查库存的接口，MCP 给它套个"说明书"让模型看懂怎么用。

### 22. Agent Skill 和 Function Calling 是一回事吗？

- **一句话**：不是。Skill 是给 Agent 的"能力包"（知识+流程+工具）；FC 是具体调一次工具。Skill 内部可能用 FC。
- **人话**：Skill="我会做饭这个本领"，FC="我现在去拿盐这个动作"。
- **你项目**：WorkBuddy 的 skill 机制就类似 Skill。

### 23. 结构化输出失败后怎么处理？

- **一句话**：重试一次(换 seed/温度) → 降级(返回错误给用户/兜底解析) → 关键场景人工介入。
- **人话**：第一次格式错了，让模型再试；还不行就老实报错别硬凑，或走人工。
- **你项目**：`ParserService` 校验失败返回结构化错误 `{field, reason, hint}`，前端能展示哪错了。

### 24. 工具调用为什么必须做安全治理？

- **一句话**：工具能改库/发钱/删文件，模型可能乱调；需白名单、参数校验、权限、human-in-the-loop（人在回路，关键操作交人确认）、审计。
- **人话**：模型说"删库"，你不能真删；危险操作得人点确认。
- **你项目**：任务53 Loop Engineering 里"大改布局/删多节点"可做人确认，即 human-in-the-loop。

### 25. 一句话概括结构化输出？

- **一句话**："用 Schema 和约束解码，把模型的自由文本变成业务系统能直接用的、字段确定的数据。"

## 四、AI 应用评测

### 26. 为什么不能只靠公开 benchmark 评估 AI 应用？

- **一句话**：公开榜测"通用能力"，不测你业务场景/数据分布/Prompt 效果；得有自己的 Golden Set（黄金测试集，代表性输入输出对）。
- **人话**：高考状元不一定会修你家水管；通用排名不代表你这摊事干得好。

### 27. Golden Set 怎么建？冷启动没日志怎么办？

- **一句话**：人工标注覆盖边界的代表样例；冷启动用"模型生成+人工校正 / 竞品输出 / 合成数据"。
- **人话**：先攒一批"标准问答"当考题；没真实数据就先用模型造、人改，或抄竞品答案当参考。

### 28. LLM-as-Judge（用另一个大模型当考官打分）有哪些偏差？怎么缓解？

- **一句话**：偏差=位置偏好、冗长偏好、自我偏好(偏好自己生成的)、格式偏好；缓解=多 judge 互评、给评分标准(rubric)、对比评测、人工抽检。
- **人话**：考官也有偏爱——答案长它就觉得好、放前面的它就给高分。得交叉打分+给明确标准+人抽查。
- **你项目**：阶段六任务51 可观测性里可接 judge 做自动评分。

### 29. RAG 评测为什么必须分检索和生成两段？

- **一句话**：检索看"召回对不对/相关不"（上下文质量）；生成看"答案用没用上、准不准"（生成质量）。问题在不同环节。
- **人话**：答错可能是"检索到的资料就错了"（检索锅），也可能"资料对但模型没用"（生成锅），得分开查。

### 30. Agent 评测为什么比普通问答/RAG 更复杂？

- **一句话**：多步、有状态、调工具、路径多样，难定义"标准答案"；要测轨迹合理性+最终效果+工具正确性。
- **人话**：问答有标准答；Agent 走三步也能对，路径不唯一，还得看它调工具对不对。

### 31. 离线评测 / Trace 回放 / 线上灰度分别解决什么？

- **一句话**：离线=固定集测改动效果；Trace 回放=用真实请求重放比对；线上灰度=小流量验证真实指标。各管不同风险。
- **人话**：离线是"模拟考"，回放是"拿真实考卷重做"，灰度是"先让一小批用户真用看数据"。

### 32. CI 里 AI 评测如何平衡速度和覆盖？

- **一句话**：小 Golden Set 快跑(回归防退化) + 抽样大模型 judge + 慢全量放 nightly(夜间跑)。
- **人话**：提交代码时跑小考快速拦错；全量大考放半夜跑不挡人。

### 33. LLM-as-Judge 和人工评测不一致怎么办？

- **一句话**：以人工为准校准 judge，分析不一致原因(标注歧义/judge 偏差)，迭代 judge 提示词，不盲目信自动。
- **人话**：考官和真人打分吵起来，先信真人，再查是题出歧义还是考官有偏向，改考官。

## 五、综合场景题（必考，结合链路答）

### 34. 客服机器人历史会话持续增长，如何分配 Token 预算并保留关键业务状态？

- **答**：历史用滑动窗口/摘要压缩（只留最近 N 轮 + 关键状态结构化存，如订单号、用户意图）；RAG 取相关知识不堆全量；关键业务状态放"结构化槽位"而非塞进对话文本。
- **人话**：老聊天别全带着，总结成一句话；订单号这种重要信息单独存，别埋在长对话里被淹没。

### 35. 流式响应中途断开，服务端如何处理重试/续传/重复计费？

- **答**：用 request_id 去重；断点用 cursor（游标，记录生成到哪）续传已生成部分不重算，或整段重生成但 client 去重避免重复计费；成本按实际输出 token 算。
- **人话**：断了重连，已吐的字不算两遍钱；用唯一 id 认出"这是同一次请求的续传"。

### 36. 上游触发 RPM/TPM 限制，网关如何排队/降级/切换模型？

- **答**：网关令牌桶排队；超时降级到小模型或返回缓存；主模型满切备用 provider（fallback）。
- **人话**：堵车了，要么排队等，要么换小车先走，要么用缓存顶一下。
- **你项目**：任务34 已有 provider fallback，正是"切备用"那一步。

### 37. 模型生成"退款工具"的调用参数后，业务系统还要执行哪些校验？

- **答**：参数范围/权限/余额/幂等/业务规则校验，不能盲信模型；关键操作 human-in-the-loop。
- **人话**：模型说"退 100 块"，你得先查这人真有这订单、余额够、没重复退，才真退。

### 38. 更换模型或修改 Prompt 后，如何验证效果？

- **答**：离线 Golden Set 比效果 → Trace 回放比真实请求 → 线上灰度小流量看指标(成本/质量/延迟)。
- **人话**：先模拟考，再拿真实卷重做，最后放一小撮真用户试，三步都过才全量。
